Find Minimum in Rotated Sorted Array

LeetCode 153 · Medium · Pattern: binary search for the pivot · O(log n) time, O(1) space

Problem. A sorted array with distinct values was rotated at some pivot. Return the minimum element.
[3,4,5,1,2] → 1    [4,5,6,7,0,1,2] → 0    [11,13,15,17] → 11
Link: LeetCode

1. The one idea that solves it

The minimum is the only point where the array drops. Everywhere else it goes up. Compare nums[mid] with nums[hi]:

  • If nums[mid] > nums[hi], the drop (and therefore the minimum) is strictly to the right of mid. The whole left side including mid is above the minimum, discard it. lo = mid + 1.
  • Otherwise nums[mid] ≤ nums[hi], so the right side [mid..hi] is already sorted and nums[mid] is a candidate for the minimum of that side. Discard the right of mid, but keep mid itself. hi = mid.

Shrink until lo == hi; that cell is the minimum. The loop is while (lo < hi) because we stop one short of equal to avoid an infinite loop (since hi = mid does not strictly shrink).

Idea. Compare nums[mid] with nums[hi]. The minimum lives on the side that still has the "drop". Half-open shrinking: lo = mid + 1 or hi = mid, loop while lo < hi, answer is nums[lo].

Why we compare against hi, not lo

Picking nums[lo] as the anchor breaks on the unrotated case [1,2,3,4]: everything is ≥ nums[lo], so you cannot tell which side the min is on without a special case. Comparing to nums[hi] handles both rotated and unrotated with one rule: nums[mid] ≤ nums[hi] means mid is in the sorted right suffix (so include it and shrink from the right), nums[mid] > nums[hi] means the pivot is between them.

4. Code (C++)

class Solution {
public:
    int findMin(vector<int>& nums) {
        int lo = 0, hi = (int)nums.size() - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] > nums[hi]) lo = mid + 1;   // min is strictly right of mid
            else                      hi = mid;       // min is at mid or left of it
        }
        return nums[lo];
    }
};

Complexity: each step halves the window, O(log n) time, O(1) space.

5. The part interviewers ask about: hi = mid, not hi = mid - 1

When nums[mid] ≤ nums[hi], nums[mid] itself could be the minimum, so we cannot drop it. The update hi = mid keeps it in the window. That is also why the loop is lo < hi (not ≤): with hi = mid, a one-cell window would recurse on itself forever under a ≤ loop.

Mirror observation: the other branch does lo = mid + 1 because nums[mid] > nums[hi] guarantees mid is not the minimum (there is at least nums[hi] below it), so we can safely exclude it.

LC 154 variant (duplicates allowed). With duplicates nums[mid] == nums[hi] gives no useful info. The fix is hi-- on equality. Worst case O(n), still O(log n) in expectation.

// LC 154: duplicates allowed
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if      (nums[mid] > nums[hi]) lo = mid + 1;
    else if (nums[mid] < nums[hi]) hi = mid;
    else                           hi--;        // cannot tell, inch down
}

6. Traps and edge cases

  • Loop condition lo ≤ hi with hi = mid. Infinite loop. Use lo < hi.
  • hi = mid - 1 on the ≤ branch. You can drop the minimum. Writing hi = mid keeps it alive.
  • Not rotated. [1,2,3,4,5]: nums[mid] ≤ nums[hi] every step, hi shrinks to lo = 0, returns nums[0] = 1. Correct.
  • Length 1. [7]: loop never runs, returns nums[0] = 7.
  • Rotated by n (equivalent to not rotated). Same case as above.
  • Rotated by exactly 1. [2,1]: lo=0, hi=1, mid=0, nums[0]=2 > nums[1]=1, so lo = 1. Return nums[1] = 1.
  • Overflow on (lo + hi) / 2. Not with LC bounds, but write lo + (hi - lo) / 2 anyway.

7. How to say it in the interview (30 seconds)

"A rotated sorted array has one 'drop'. I compare nums[mid] with nums[hi]: if nums[mid] > nums[hi], the drop and therefore the minimum is strictly to the right, so lo = mid + 1. Otherwise the right half from mid is sorted, so the minimum is at mid or to its left, so hi = mid. I stop at lo == hi. O(log n). Comparing to hi (not lo) covers the unrotated case with no special code."
