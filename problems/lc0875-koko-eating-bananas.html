Koko Eating Bananas

LeetCode 875 · Medium · Pattern: binary search on the answer · O(n log M) time, O(1) space

Problem. Piles of bananas. Each hour Koko picks one pile and eats up to k bananas from it (if the pile has less, she still rests the rest of the hour). Find the smallest integer eating speed k that finishes all piles in h hours.
piles=[3,6,7,11], h=8 → 4    piles=[30,11,23,4,20], h=5 → 30
Link: LeetCode

1. The one idea that solves it

Call f(k) the number of hours needed at speed k:

f(k) = ∑p ∈ piles ⌈p / k⌉

As k grows, each ceiling can only drop or stay the same, so f is a non-increasing function of k. The question "is this speed fast enough?" (f(k) ≤ h) is therefore monotonic: false for small k, true from some point onward. Binary search for that boundary.

Range: k must be at least 1 (she has to eat something) and never needs to exceed max(piles) (finishing the biggest pile in one hour per pile is already n ≤ h hours by the constraints). So search k in [1, max(piles)].

Idea. Binary search on k, not on an index. The predicate hours(k) ≤ h flips from false to true at the answer. Use the standard lower-bound template to find the first k where it is true.

Why ceiling, not floor

At speed k = 4 on a pile of 7, Koko eats 4 the first hour (3 left), then 3 the second hour (she does not keep going into a third pile that hour). That is 2 hours = ⌈7 / 4⌉. Floor would give 1 and undercount. Compute ceiling with integer math: (p + k - 1) / k.

4. Code (C++)

class Solution {
public:
    int minEatingSpeed(vector<int>& piles, int h) {
        int lo = 1, hi = *max_element(piles.begin(), piles.end());
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            long long hours = 0;
            for (int p : piles) hours += (p + mid - 1) / mid;   // ceil(p / mid)
            if (hours <= h) hi = mid;                              // fast enough, try slower
            else            lo = mid + 1;                          // too slow
        }
        return lo;
    }
};

Complexity: O(n log M) where M = max(piles). One n-length sum per binary-search step, and the step count is log M. O(1) extra space.

5. The part interviewers ask about: why hours fits in long long

LeetCode bounds: 1 ≤ piles[i] ≤ 109 and n ≤ 104. At mid = 1, each ceiling is up to 109 and we sum n of them, so the total can reach 1013. That overflows a 32-bit int. Use long long for the running sum (or break early once hours > h, which also stops the overflow).

Early exit. Once hours exceeds h you already know this mid is too slow. Breaking out saves work and avoids the overflow concern:

for (int p : piles) {
    hours += (p + mid - 1) / mid;
    if (hours > h) break;
}

Why the final return lo, not return hi, is right. The loop is the half-open template: on exit lo == hi and that index is the first speed where the predicate holds. The predicate is "hours(k) ≤ h", which is exactly the condition in the problem statement, so lo is the answer.

6. Traps and edge cases

  • Floor instead of ceiling. Using p / mid undercounts hours and returns a speed that is actually too slow.
  • mid = 0. With lo = 0 you can get mid = 0 and divide by zero. Start lo = 1.
  • Integer overflow in the sum. See the box above. Use long long.
  • hi = max(piles) + 1 instead of max(piles). Harmless but wasteful. At speed max(piles), every pile takes exactly one hour, total n hours, and the constraints say n ≤ h, so max(piles) always satisfies the predicate.
  • Mixing closed and half-open templates. If the loop is lo < hi you must write hi = mid, not hi = mid - 1. The latter can skip the answer when the window is two cells.
  • Single pile. piles = [1000000000], h = 2: binary search converges to ⌈109 / 2⌉ = 500000000.

7. How to say it in the interview (30 seconds)

"The hours needed at speed k is ∑⌈p / k⌉, which is non-increasing in k. So hours(k) ≤ h flips from false to true once as k grows: that is a binary-search condition. I search k in [1, max(piles)] with the lower-bound template: hi = mid when fast enough, lo = mid + 1 when too slow, return lo. Use ceiling for the per-pile hours, and long long for the sum to avoid overflow at k = 1."
