Word Break II

LeetCode 140 · Hard · Pattern: memoised DFS over suffixes · O(n · 2n) output in the worst case, O(n · max answers) memo space

Problem. Given string s and dictionary wordDict, return all ways to split s into dictionary words, each joined by a single space.
s = "catsanddog", dict = ["cat","cats","and","sand","dog"] → ["cats and dog","cat sand dog"]
s = "pineapplepenapple", dict = ["apple","pen","applepen","pine","pineapple"] → 3 splits
s = "catsandog", dict = ["cats","dog","sand","and","cat"] → []
Link: LeetCode

1. The one idea that solves it

Think about the first word of the answer. It is some prefix s[0..i) of s that happens to be in the dictionary. The rest of the answer is "all splits of the suffix s[i..n)". So the whole thing is recursive:

splits(s) = ⋃ i : s[0..i) ∈ dict   prefix ⊕ splits(s[i..n))

Without memoisation this is exponential: "aaaaab" with dict = {"a","aa"} recomputes splits("aaaab"), splits("aaab"), … many times. Each suffix is a reusable sub-problem, so memoise by suffix: memo[suffix] → all its splits.

Idea. Pick the first word, recurse on the rest, cache by suffix. The same suffix is reached by many different prefix choices higher up, and the memo collapses them all into one computation. If LC 139 asks "is a split possible?", LC 140 asks "list them all" — the shape is the same, we just return a list of strings instead of a boolean.

2. Picture of the algorithm

Why memoising the suffix is enough: the set of splits of s[i..n) depends only on i, not on how we reached i from the top. Two different callers who both land on the suffix starting at index i see the same answer, so one computation serves both.

Output size matters here. The number of splits can be exponential in n (e.g. all-a string with dict {"a","aa"} grows like Fibonacci). Memoisation makes the work per distinct suffix polynomial, but we still spend time proportional to the number of answers because we have to list them.

4. Code (C++)

class Solution {
    unordered_set<string> dict;
    unordered_map<string, vector<string>> memo;

    vector<string> dfs(const string& s) {
        auto it = memo.find(s);
        if (it != memo.end()) return it->second;    // memo hit

        vector<string> result;
        if (dict.count(s)) result.push_back(s);           // whole suffix is a word

        for (int i = 1; i < (int)s.size(); i++) {
            string prefix = s.substr(0, i);
            if (dict.count(prefix)) {
                auto rest = dfs(s.substr(i));
                for (auto& r : rest)
                    result.push_back(prefix + " " + r);
            }
        }
        return memo[s] = result;
    }
public:
    vector<string> wordBreak(string s, vector<string>& wordDict) {
        dict = unordered_set<string>(wordDict.begin(), wordDict.end());
        memo.clear();
        return dfs(s);
    }
};

Complexity. Each distinct suffix is computed once; there are at most n of them. Per suffix we try O(n) prefix cuts (each a substring and a hash probe, O(L) where L is the prefix length), plus we concatenate every returned split. The output can be exponential, so the total time is O(n2 · L + n · total answer length). Space is the memo, bounded by the total length of all stored splits plus the recursion depth O(n).

Alternative: do LC 139 first, then recurse

bool reachable[n + 1];                         // LC 139 style
// Fill reachable[i] = can s[i..n) be split? Then DFS only enters
// a branch where reachable[i] is true. Avoids wasted recursion
// on suffixes that cannot be split at all.

Prefer this when the dictionary rarely matches and you'd otherwise walk long dead branches. The direct memoised version is fine when most suffixes do split.

5. The part interviewers ask about: why memoise the suffix, not the index?

Memoising by index i and by suffix s.substr(i) are equivalent: the suffix is a function of i and the fixed s. Suffix is clearer in interviews because it exposes what the sub-problem is; index is faster in code because the hash key is cheaper. Either answer is fine; be ready to switch if the interviewer pushes on cost.

A second subtle point: the stored answer is the splits of the suffix on its own, not pre-pended with any prefix. That is what makes caching valid — two callers reuse the same list because it says nothing about where they came from. If you store fullAnswer = prefix + " " + rest in the cache, you lose reusability.

Third thing people ask: can we build this bottom-up with 1-D DP like LC 139? Yes, with dp[i] = list of splits of s[i..n), filled from i = n downwards. It's the same algorithm in a different direction; most people find top-down + memo easier to write under pressure.

6. Traps and edge cases

  • Forgetting to catch the "whole suffix is a word" case. If s itself is in the dictionary, s is a valid split of length one. Easy to miss when the loop starts at i = 1 and ends at i < s.size().
  • Caching the pre-pended answer. Cache only the splits of the suffix on its own. Prepending a prefix at cache time poisons the entry for other callers.
  • Returning result without storing it. The memo[s] = result assignment is what gives the next identical call its O(1) exit. Without it the algorithm regresses to exponential.
  • Treating wordDict as a vector. O(|dict|) lookup per prefix wrecks the running time. Use unordered_set.
  • Blow-up inputs. s = "aaaaaaaaaaaaaaaaaaaaab" with dict = {"a","aa","aaa",...} has no split (the b doesn't match), but naive DFS explores every partition of the a's. Memoisation on the suffix returns immediately on the second visit; LC 139-style reachability as a filter is better still.
  • Empty dictionary. If no word matches any prefix, return []. The code handles it: the loop adds nothing and the suffix is not in dict.

7. How to say it in the interview (30 seconds)

"I pick the first word: any dictionary prefix of s. The rest of the answer is all splits of the remaining suffix, which is a sub-problem of the same shape. I DFS on suffixes and memoise by suffix, so each distinct suffix is solved once. If the whole suffix is itself in the dictionary, that counts as a split too. Time is O(n2) per distinct suffix, plus the total length of the output, which is intrinsic because we have to list every split. If dead branches hurt, I first run LC 139 to mark which suffixes split at all and only recurse into those."
