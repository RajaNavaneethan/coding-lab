Range Sum Query 2D - Immutable

LeetCode 304 · Medium · Pattern: 2D prefix sum · O(R·C) build, O(1) per query, O(R·C) space

Problem. Design NumMatrix(matrix) with sumRegion(r1, c1, r2, c2) returning the sum of the rectangle with top-left (r1,c1) and bottom-right (r2,c2), inclusive. Many queries are made, so each must be fast.
Example: the 5×5 matrix below, sumRegion(2,1,4,3) → 8, sumRegion(1,1,2,2) → 11, sumRegion(1,2,2,4) → 12.   Link: LeetCode

1. The one idea that solves it

Precompute P[r][c] = the sum of every cell above and to the left of (r,c), that is the rectangle from (0,0) to (r−1,c−1). The table has one extra row and column of zeros so the edges need no special cases.

Any rectangle is then a big top-left rectangle minus the strip above it, minus the strip to its left, plus the corner that was subtracted twice. That is four lookups, whatever the size of the rectangle.

sum = P[r2+1][c2+1] − P[r1][c2+1] − P[r2+1][c1] + P[r1][c1]

Building the table uses the same picture backwards: the prefix up to a cell is the cell itself, plus the prefix above, plus the prefix to the left, minus the overlap counted twice.

P[r+1][c+1] = m[r][c] + P[r][c+1] + P[r+1][c] − P[r][c]
Idea. Pay O(R·C) once to build a padded 2D prefix table. Every query is then inclusion-exclusion on four corners: add the full block, subtract the block above and the block to the left, add back the doubly subtracted corner.

4. Code (C++)

class NumMatrix {
    vector<vector<int>> P;                       // (R+1) x (C+1), row 0 and col 0 are zeros
public:
    NumMatrix(vector<vector<int>>& m) {
        int R = m.size(), C = R ? m[0].size() : 0;
        P.assign(R + 1, vector<int>(C + 1, 0));
        for (int r = 0; r < R; r++)
            for (int c = 0; c < C; c++)
                P[r + 1][c + 1] = m[r][c] + P[r][c + 1] + P[r + 1][c] - P[r][c];
    }
    int sumRegion(int r1, int c1, int r2, int c2) {
        return P[r2 + 1][c2 + 1] - P[r1][c2 + 1] - P[r2 + 1][c1] + P[r1][c1];
    }
};

Complexity: the constructor visits each cell once with O(1) work, so O(R·C) time and space. Each query reads four cells, so O(1).

5. The part interviewers ask about: why the extra row and column?

Without padding, a query with r1 = 0 or c1 = 0 would read P[-1][..], so you'd need three special cases. Shifting everything by one and keeping a row and column of zeros means "the strip above row 0" is simply zero. Both the build formula and the query formula then work for every cell with no branches. Expect follow-ups: "what if the matrix changes?" Then rebuilding is O(R·C) per update; use a 2D Fenwick tree (LC 308) for O(log R · log C) updates and queries.

6. Traps and edge cases

  • Off-by-one in the query. The bottom-right corner is P[r2+1][c2+1], but the subtracted strips use r1 and c1 without +1. Mixing these up drops or double-counts a row.
  • Forgetting to add back P[r1][c1]. The top-left block was subtracted twice.
  • Summing the rectangle in each query. O(R·C) per query; times out with 104 queries.
  • Empty matrix. m[0].size() on an empty matrix is undefined behaviour; guard with R ? m[0].size() : 0.
  • Overflow. With 200×200 cells of |v| ≤ 105, totals reach 4·109 in the worst case. LeetCode's tests fit in int, but say you'd use long long for safety.
  • Single cell. sumRegion(0,0,0,0) returns m[0][0] = 3 for the example.

7. How to say it in the interview (30 seconds)

"Since there are many queries, I precompute a 2D prefix table where each entry is the sum of everything above and to the left, with an extra zero row and column so edges need no special cases. Building it uses the cell plus top plus left minus the overlap. A query is inclusion-exclusion on four corners: the full block, minus the block above, minus the block to the left, plus the corner I subtracted twice. Build is O(rows times cols), each query is O(1)."
