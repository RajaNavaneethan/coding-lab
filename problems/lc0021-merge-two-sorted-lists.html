Merge Two Sorted Lists

LeetCode 21 · Easy · Pattern: two-pointer weave with a dummy head · O(n+m) time, O(1) space

Problem. You are given the heads of two sorted linked lists l1 and l2. Splice them together into one sorted list by reusing the existing nodes (no new nodes), and return its head.
[1,2,4] + [1,3,4] → [1,1,2,3,4,4].    Link: LeetCode

1. The one idea that solves it

Walk two pointers down the two lists in parallel. At every step the smaller current head is the next node of the answer, so append that node to the tail of your result and advance only that pointer. When one list runs out, the other's remainder is already sorted, so you just attach it in one move.

The one small bookkeeping trick is a dummy head node. Then "the tail" is always a real node and the first node you attach needs no special case.

Idea. Keep a tail pointer. While both lists have nodes, pick the smaller head, link it after tail, and advance that list and tail. When the loop ends, append whichever list is non-empty. Return dummy.next.

2. Picture of the algorithm

Each step consumes exactly one input node and extends the output by one. When either input runs out, the remaining chain already is sorted, so tail->next = l1 ? l1 : l2 finishes the job in one assignment. No node is copied; the pointers are just rewired.

3. Step-by-step trace

just picked current heads (l1 / l2) in the output not yet consumed

4. Code (C++)

ListNode* mergeTwoLists(ListNode* l1, ListNode* l2) {
    ListNode dummy(0);                      // stack-allocated sentinel
    ListNode* tail = &dummy;
    while (l1 && l2) {
        if (l1->val <= l2->val) {
            tail->next = l1; l1 = l1->next;
        } else {
            tail->next = l2; l2 = l2->next;
        }
        tail = tail->next;
    }
    tail->next = l1 ? l1 : l2;              // one of them is null, the other is the tail
    return dummy.next;
}

Complexity: each node is linked once, so O(n+m) time. Only the dummy, tail, and the two head pointers; no new nodes. O(1) extra space.

Alternative: recursive

ListNode* mergeTwoLists(ListNode* l1, ListNode* l2) {
    if (!l1) return l2;
    if (!l2) return l1;
    if (l1->val <= l2->val) {
        l1->next = mergeTwoLists(l1->next, l2);
        return l1;
    } else {
        l2->next = mergeTwoLists(l1, l2->next);
        return l2;
    }
}

Prefer when the interviewer wants to see recursion or when you are inside a merge-sort step on linked lists (LC 148). Costs O(n+m) stack space, which is fine up to about 104 nodes but risky at 105. The iterative version with a dummy is the default.

5. The part interviewers ask about: use ≤, not <

Stability. When the two heads tie, picking from l1 keeps the merge stable: equal values from the first list come out before equal values from the second. Stability is irrelevant for the final sorted values here, but as a merge-sort subroutine (LC 148) stability can matter, and it makes the trace deterministic. Use <=, not <.

A second small point: the dummy head is a sentinel, not output. Return dummy.next, not &dummy. The dummy is stack-allocated here, so you don't leak or need to delete it. If you build the dummy with new, remember to delete it before returning (or stop using new for sentinels).

A third angle an interviewer may probe: space-wise this is zero extra because we splice existing nodes. A beginner may write code that allocates a new list and copies values, which still runs in O(n+m) time but costs O(n+m) extra memory. The splice version is strictly better.

6. Traps and edge cases

  • Both lists empty. dummy.next is nullptr; the loop never runs; the final assignment picks the null branch. Correct.
  • One list empty. Loop body never runs; the final line attaches the non-empty list. Correct.
  • Forgetting to advance tail. You keep overwriting tail->next and only the last picked node survives.
  • Advancing tail = tail->next->next. Skips a node. Easy to type by accident.
  • Using < instead of ≤. On ties the merge is no longer stable (same final multiset, but different node order). Harmless here; a real bug in LC 148.
  • Returning &dummy or dummy. You hand back the sentinel with value 0 glued to the front of the real answer. Always return dummy.next.
  • Allocating new nodes to hold the values. Works, but wastes O(n+m) memory and loses marks on the space-complexity follow-up.

7. How to say it in the interview (30 seconds)

"I keep a dummy head and a tail pointer. While both lists have nodes, I compare the heads, link the smaller one after tail, and advance that list and tail. When one list is empty, I attach the other's remainder in one assignment and return dummy.next. I use ≤ to keep the merge stable. One pass over both lists, O(n+m) time, O(1) extra space because I'm splicing existing nodes, not copying."
