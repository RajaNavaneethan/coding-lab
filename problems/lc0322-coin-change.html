Coin Change

LeetCode 322 · Medium · Pattern: 1-D DP (unbounded coins) · O(amount · |coins|) time, O(amount) space

Problem. Given coin denominations coins[] (unlimited copies of each) and an amount, return the fewest coins that sum to amount, or -1 if impossible.
coins = [1,2,5], amount = 11 → 3 (11 = 5+5+1)    coins = [2], amount = 3 → -1    amount = 0 → 0
Link: LeetCode

1. The one idea that solves it

Define dp[a] as the fewest coins that sum to a. To make a you must end with some coin c; before that coin was added, the running total was a − c, which itself takes dp[a−c] coins. So:

dp[a] = 1 + min over c in coins of dp[a − c]

Base dp[0] = 0 (empty bag). All other cells start at a sentinel "impossible" value (amount + 1, which is larger than any real answer). After the fill, dp[amount] > amount means no combination exists.

Idea. Fix any optimal multiset of coins that sums to a, strip off any one coin c. The rest is an optimal multiset for a − c. So the optimum at a is the best "add one coin" extension of some smaller optimum.

2. Picture of the algorithm

The outer loop walks a from 1 to amount. The inner loop tries every coin and keeps the one that gives the smallest dp[a − c] + 1. This is the unbounded variant (coins reusable), so the amount loop is on the outside.

4. Code (C++)

class Solution {
public:
    int coinChange(vector<int>& coins, int amount) {
        vector<int> dp(amount + 1, amount + 1); // sentinel > any real answer
        dp[0] = 0;
        for (int i = 1; i <= amount; i++) {
            for (int c : coins) {
                if (c <= i) dp[i] = min(dp[i], dp[i - c] + 1);
            }
        }
        return dp[amount] > amount ? -1 : dp[amount];
    }
};

Complexity: O(amount · |coins|) time — one min per (amount, coin) pair. O(amount) space.

Why not greedy?

Greedy "always take the largest coin that fits" works for canonical currencies (1, 5, 10, 25) but fails in general. On coins = [1, 3, 4], amount = 6 greedy gives 4 + 1 + 1 = 3 coins, but the optimum is 3 + 3 = 2 coins. DP tries every coin at every amount, so it cannot miss.

5. The part interviewers ask about: order of loops matters

This problem has a close cousin, LC 518 "Coin Change II" (count the number of distinct combinations). The code for both looks almost identical, but the order of the two loops is different:

ProblemWhat dp[a] meansOuter loopInner loop
LC 322 (this)fewest coinsamount acoin c
LC 518 (count ways)number of combinationscoin camount a
For the min-coins problem, every multiset of coins has the same answer regardless of order (3 + 1 and 1 + 3 both cost two coins). So the "amount outer, coin inner" loop that counts ordered sequences gives the right min, because the min of the same values is the same no matter in which order you take them.

For counting combinations, order matters: "amount outer, coin inner" would double-count 1+2 and 2+1 as two ways. Swapping to "coin outer, amount inner" fixes it: each coin is only considered once in the outer loop, so you count combinations, not permutations.

6. Traps and edge cases

  • Initialising with INT_MAX. Then dp[i - c] + 1 overflows to a negative number and the min picks it. Use a sentinel like amount + 1.
  • Returning dp[amount] directly. Must check for the sentinel and return -1 in the impossible case.
  • amount = 0. Zero coins. The dp[0] = 0 base handles it; just return 0.
  • Coin value > amount. The if (c <= i) guard skips it. Without it, you index with a negative subscript.
  • Trying to recover the coins. You need either a parent[a] array that remembers which coin was chosen at a, or a second pass that walks back from amount using the DP values.
  • Confusing with LC 518. Different problem, different loop order, different sentinel (count starts at 0, not +∞).

7. How to say it in the interview (30 seconds)

"I define dp[a] as the fewest coins summing to a. Any optimal solution ends with some coin c, so dp[a] = 1 + min_c dp[a−c] over coins with c ≤ a. I fill dp from 1 to amount, using a sentinel amount + 1 for "impossible", so the only check at the end is dp[amount] > amount ? -1 : dp[amount]. That's O(amount · |coins|) time and O(amount) space. Greedy fails on inputs like coins [1,3,4], amount 6 where DP finds 3 + 3."
