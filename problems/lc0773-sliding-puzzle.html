Sliding Puzzle

LeetCode 773 · Hard · Pattern: BFS over implicit state-graph · O(|states| · log|states|) time with hashing, O(|states|) space; |states| = 6!/2 = 360 reachable

Problem. You have a 2 × 3 board with tiles 1..5 and one empty cell (represented as 0). One move slides the empty cell up/down/left/right by swapping it with its neighbour. Find the minimum number of moves to reach the goal [[1,2,3],[4,5,0]], or -1 if impossible.
[[1,2,3],[4,0,5]] → 1
[[1,2,3],[5,4,0]] → -1 (unreachable half of state space)
[[4,1,2],[5,0,3]] → 5
Link: LeetCode

1. The one idea that solves it

Forget "tiles move". Each board configuration is a node; two boards are connected by an edge whenever one move turns one into the other. Edges have unit cost, so shortest path from start to goal is BFS. The state graph is small (6! = 720 permutations, half reachable from any given start) so BFS fits comfortably in memory and runs in milliseconds.

The one engineering trick: encode a board as a string of six characters, e.g. "123450". Strings go into an unordered_set for O(1) "seen before" checks and into a queue with their distance. Neighbours are generated by swapping the '0' with each of its adjacent positions, where "adjacent" is fixed by the 2×3 shape and precomputed as a 6-entry neighbour table.

Idea. The implicit graph has one vertex per board layout and one edge per legal slide. Unweighted shortest path = BFS. Encode each board as a string so visited states are hashable in one step; use a precomputed adjacency table on the six flat positions to generate neighbours without index gymnastics.

2. Picture of the algorithm

The 2×3 shape fixes the neighbour table once and for all:

flat positions:   0 1 2
                  3 4 5

neighbours[0] = {1, 3}        neighbours[1] = {0, 2, 4}      neighbours[2] = {1, 5}
neighbours[3] = {0, 4}        neighbours[4] = {1, 3, 5}      neighbours[5] = {2, 4}

Encoded boards: find '0', look up its neighbours in the table, swap, check against the seen set, push.

4. Code (C++)

class Solution {
public:
    int slidingPuzzle(vector<vector<int>>& board) {
        string start, target = "123450";
        for (auto& row : board)
            for (int v : row) start += char('0' + v);
        if (start == target) return 0;

        // Neighbours of each flat position in a 2x3 grid.
        vector<vector<int>> adj = {
            {1, 3}, {0, 2, 4}, {1, 5},
            {0, 4}, {1, 3, 5}, {2, 4}
        };

        unordered_set<string> seen{start};
        queue<pair<string, int>> q;
        q.push({start, 0});

        while (!q.empty()) {
            auto [s, d] = q.front(); q.pop();
            int zero = s.find('0');
            for (int nb : adj[zero]) {
                string ns = s;
                swap(ns[zero], ns[nb]);
                if (ns == target) return d + 1;
                if (!seen.count(ns)) { seen.insert(ns); q.push({ns, d + 1}); }
            }
        }
        return -1;
    }
};

Complexity. At most 6! = 720 states ever enter the queue, each generates at most 4 neighbours, and each check is O(1) hash + O(6) string copy. So O(1) in the problem's fixed-size sense, but O(|states|) if generalised. Space is the seen set, bounded by the number of reachable states (360 from any start whose parity matches the goal).

Alternative: A* with Manhattan distance

For n × m generalisations ("n-puzzle"), A* with the sum of Manhattan distances from each tile to its goal is standard. Manhattan is admissible (every tile needs at least that many slides) and the search explores far fewer states. On the 2×3 board, plain BFS beats A* in code size without hurting running time (360 states fit easily).

5. The part interviewers ask about: half the states are unreachable

Treat the empty cell as "tile 6" on 6 cells and count the parity of the permutation of 1..6. Every legal slide swaps two adjacent cells, which is a single transposition, so each move flips parity. The empty cell also moves grid position by one, changing its parity too. Together those two parities add up to a conserved quantity under moves — the sum of the permutation parity and the empty-cell's position parity is invariant. Boards whose combined parity differs from the goal are unreachable in any number of moves, so BFS will exhaust the reachable half and return -1.

This is why [[1,2,3],[5,4,0]] returns -1: swapping 5 and 4 is a single transposition without moving the empty cell to the right place, so it's parity-forbidden.

You don't need to compute parity; BFS discovers unreachability by exhausting the search. But if asked "how do you know when to give up?" the answer is "when the queue is empty — there are no more states to try." Mentioning the parity invariant up front is a nice interview flex.

Second question: why BFS, not DFS? We want the shortest move sequence, and all edges cost 1. DFS finds a path, not the shortest; iterative deepening would reach the same answer but costs more. BFS visits each state once at its shortest distance from the start, which is both correct and fast here.

Third: why move the empty cell instead of a tile? They're the same operation (both are "swap 0 with a neighbour") but centring on the empty cell gives at most 4 neighbours per state regardless of which tile occupies which cell. Looping over tiles would need an outer loop with up to 5 tiles plus a check that their move target is the empty cell — same answer, uglier code.

6. Traps and edge cases

  • Returning the depth of the goal when enqueued. Standard. Checking goal on dequeue is also fine; checking before entering the loop handles the "already solved" input (d = 0).
  • Hardcoding the 2×3 shape into index math. Works, but a neighbour table is far less error-prone and documents the adjacency explicitly.
  • Pushing without a seen check. Each state would re-expand, blowing the queue. The seen set is the whole point of BFS on an implicit graph.
  • Using set<string>. Correct but slower. unordered_set is O(1) per operation.
  • Mutating board in place and forgetting to restore. Not applicable here (we work on string copies), but a common bug when porting the solution to the real puzzle data structure.
  • Infinite loop on unreachable input. Shouldn't happen with the seen set — the queue drains after 360 states and the function returns -1.
  • Treating -1 as "no 0 on the board". The problem guarantees exactly one 0, so s.find('0') is always valid.
  • Starting at the goal. Return 0 immediately, don't enqueue and dequeue. The early-exit check saves a step.

7. How to say it in the interview (30 seconds)

"Each board layout is a vertex and each legal slide is a unit-weight edge, so I'm looking for the shortest path in an implicit graph, which is BFS. I flatten the board to a 6-character string, precompute the neighbour table for the six flat positions in a 2×3 grid, and BFS from the start: find the '0', swap with each adjacent position, hash-check against the seen set, enqueue new states with distance d + 1. First time I enqueue "123450" I return its distance. The state space has 6! = 720 permutations; half are unreachable by parity, so some starts return -1."
