Implement Trie (Prefix Tree)

LeetCode 208 · Medium · Pattern: Trie (prefix tree) · O(L) per operation, O(total chars) space

Problem. Build a data structure that supports three operations on lowercase strings:
insert(word) · search(word) (exact match) · startsWith(prefix) (any inserted word has this prefix).
Link: LeetCode

1. The one idea that solves it

A trie is a tree in which every edge is labelled with one character. The path from the root down to a node spells a prefix. If you also mark the nodes where an inserted word ends, then:

  • search(word) walks the path for word and returns true iff the final node is marked "end of word".
  • startsWith(prefix) walks the path and returns true iff you did not fall off the tree — the final-node mark doesn't matter.
  • insert(word) walks the path, creating any missing edges, and marks the final node as "end of word".

Each node holds a 26-slot child array (one slot per lowercase letter) and a boolean end. The whole tree stores one node per distinct prefix of all inserted words, which is bounded by the total length.

Idea. Share common prefixes across words by walking character by character and splitting only when they differ. Each operation is O(L) in the length of the input, independent of how many words are already in the trie.

2. Picture of the algorithm

insert and search have the same walking skeleton; they differ only in what happens when a child is missing (insert creates it, search returns false) and in what happens at the end (insert marks end, search reads it, startsWith ignores it).

4. Code (C++)

class Trie {
    struct Node {
        Node* ch[26] = {};        // nullptr by default
        bool end = false;
    };
    Node* root;
    Node* walk(const string& s) const {
        Node* cur = root;
        for (char c : s) {
            int i = c - 'a';
            if (!cur->ch[i]) return nullptr;
            cur = cur->ch[i];
        }
        return cur;
    }
public:
    Trie() { root = new Node(); }
    void insert(string word) {
        Node* cur = root;
        for (char c : word) {
            int i = c - 'a';
            if (!cur->ch[i]) cur->ch[i] = new Node();
            cur = cur->ch[i];
        }
        cur->end = true;
    }
    bool search(string word) {
        Node* n = walk(word);
        return n && n->end;
    }
    bool startsWith(string prefix) {
        return walk(prefix) != nullptr;
    }
};

Complexity: O(L) per op where L is the string length. Each step is one array index. Space is O(total number of distinct prefixes) ≤ sum of inserted word lengths. The 26-slot array per node is the simplest form; swap for a unordered_map<char, Node*> if the alphabet is large or sparse.

Alternative: hash-map children

struct Node { unordered_map<char, Node*> ch; bool end = false; };

Prefer when the alphabet is big (Unicode, mixed case, digits) or when most nodes have few children, so the dense 26-array wastes memory. Pure speed on lowercase English, the array version wins.

5. The part interviewers ask about: three subtle points

  • end is per node, not per edge. Two words sharing a prefix (like app and apple) are both marked by setting end = true at the respective nodes; the shorter word's end sits on an internal node of the longer word.
  • startsWith ignores end. It only asks whether the path exists in the tree. That is also why inserting apple alone makes startsWith("app") return true, but search("app") false.
  • Empty string. The root always exists, so startsWith("") is true and search("") is false unless the empty string was inserted (which marks the root's end).

Why a trie beats a hash set of words

unordered_set<string> supports insert and search in O(L) too (hash and compare), but startsWith would need to scan every stored word. A trie answers startsWith in O(L), independent of how many words were inserted. That is the whole reason the data structure exists.

6. Traps and edge cases

  • Forgetting to mark end. Then search always returns false. The startsWith check still works, which can mask the bug.
  • Confusing search and startsWith. startsWith does not check end; search must.
  • Leaking memory. On LeetCode this doesn't fail the judge, but a destructor that frees nodes (recursive DFS) is good hygiene — and in interview follow-ups ("add remove") you need the structure for it.
  • Non-ASCII input. c - 'a' blows up on uppercase or digits. If the problem allows them, use a hash map for children.
  • Reinsertion. Inserting the same word twice is a no-op (end stays true). Make sure your code does not double-count or crash.
  • Deleting. Not asked here, but naive deletion of a word w is "clear end at the end of w; walk up and prune nodes whose end is false and whose children are all nullptr." Pruning early (before clearing) is a common bug.

7. How to say it in the interview (30 seconds)

"I use a trie: each node has a 26-slot child array and an end flag. insert walks the word one letter at a time, creating missing children, and marks the final node end = true. search walks the word and returns end at the final node (false if we fell off). startsWith walks the prefix and returns true iff we didn't fall off, ignoring end. All three are O(L). The whole structure stores one node per distinct prefix, so space is O(total inserted characters)."
