Find Median from Data Stream

LeetCode 295 · Hard · Pattern: two balanced heaps · O(log n) add, O(1) median

Problem. Design a data structure that supports:
  • addNum(num) — add an integer to the stream.
  • findMedian() — return the median so far. If the count is even, return the mean of the two middle values.
add 1, add 2, median = 1.5, add 3, median = 2.0.    Link: LeetCode

1. The one idea that solves it

Split the stream into two halves: the lower half (every number ≤ median) and the upper half (every number ≥ median). If you can always access the largest of the lower half and the smallest of the upper half, the median is one of them (odd count) or their mean (even count).

So keep two heaps: a max-heap for the lower half (so its root is the largest of the lower half) and a min-heap for the upper half (so its root is the smallest of the upper half). Keep them balanced: |lower| == |upper| or |lower| == |upper| + 1. Each add is O(log n); the median is O(1).

Idea. Lower half = max-heap, upper half = min-heap. Rebalance after every add so the max-heap has as many elements as the min-heap, or exactly one more. Median = max-heap root (odd), or average of both roots (even).

2. Picture of the algorithm

The two heaps face each other: the max-heap's root is the biggest of the lower half, the min-heap's root is the smallest of the upper half. Those two numbers sit side by side at the "spine" of the structure — that spine is the median.

3. Step-by-step trace

Input is an operation sequence. add N inserts N; median queries. After each op, the two heaps are drawn as binary trees side by side with their sizes.

just inserted / moved root contributes to the median in the heap

4. Code (C++)

class MedianFinder {
    priority_queue<int> lo;                                   // max-heap: lower half
    priority_queue<int, vector<int>, greater<int>> hi;        // min-heap: upper half

public:
    void addNum(int num) {
        if (lo.empty() || num <= lo.top()) lo.push(num);    // belongs to lower half
        else                               hi.push(num);    // strictly greater -> upper

        // Rebalance: keep |lo| == |hi| or |lo| == |hi| + 1
        if (lo.size() > hi.size() + 1) { hi.push(lo.top()); lo.pop(); }
        else if (hi.size() > lo.size()) { lo.push(hi.top()); hi.pop(); }
    }

    double findMedian() {
        if (lo.size() > hi.size()) return (double)lo.top();           // odd count
        return ((double)lo.top() + (double)hi.top()) / 2.0;         // even count
    }
};

Complexity: each addNum does O(1) heap pushes/pops, each O(log n), so O(log n) time. findMedian reads one or two roots, O(1). Space O(n) for the two heaps.

About the two comparators. priority_queue<int> is the default max-heap (uses less<int>; the "top" is whatever the comparator calls biggest, so the actual maximum). To get the min-heap on the upper half, you must spell out the full template: priority_queue<int, vector<int>, greater<int>>. The template parameters are <T, Container, Compare>, so you cannot omit the middle one. The rule: top is the element the comparator deems largest; pass greater<int> to invert.

Alternative: ordered multiset with a middle iterator

class MedianFinder {
    multiset<int> s;
    multiset<int>::iterator mid;                             // points at (n/2)-th element
public:
    void addNum(int num) {
        s.insert(num);
        if (s.size() == 1) mid = s.begin();
        else if (num < *mid)                           // inserted on the left
            { if (s.size() % 2 == 0) --mid; }
        else                                        // inserted on the right
            { if (s.size() % 2 == 1) ++mid; }
    }
    double findMedian() {
        if (s.size() % 2) return (double)*mid;
        auto next = mid; ++next;
        return ((double)*mid + (double)*next) / 2.0;
    }
};

Prefer when the interviewer also asks for deletion of arbitrary elements (multiset::erase is O(log n)); the two-heap version struggles with removes because priority_queue can't delete by value. Default to two heaps otherwise — simpler, same asymptotics.

5. The part interviewers ask about: the balance invariant

Two invariants make the whole thing work:
  1. Order. Every element of lo is ≤ every element of hi. This is what makes lo.top() actually be the biggest of the lower half.
  2. Size. lo.size() ∈ { hi.size(), hi.size() + 1 }. This is what makes the median land exactly on lo.top() (odd) or on the pair (lo.top(), hi.top()) (even).
Every call to addNum restores both: insert into the correct side (preserves order), then move one element across if the sizes went out of range (restores balance). After the two rebalance ifs, both invariants hold again.

A common follow-up: can the median be the mean of two equal values? Yes — e.g. after adding [1,1,2,2], the median is (1+2)/2 = 1.5. The code is correct because it never relies on the two roots being different; it averages them regardless.

6. Traps and edge cases

  • Which side is max-heap, which is min-heap? Lower half is max-heap (we want its biggest), upper half is min-heap (we want its smallest). Flip one, and top() gives the wrong number.
  • Default priority_queue<int> is max-heap. If you forget greater<int> on the upper half, you accidentally compare the wrong roots and get a near-random "median".
  • Convention of which heap can be bigger. Pick one — "lo has at most one more than hi" is the usual choice. The findMedian code must match: when the sizes differ, return the root of the larger heap.
  • Integer overflow when averaging two ints. On the full LeetCode range, INT_MAX + INT_MAX overflows. Cast to double (or use long long) before adding, as the code above does.
  • Query before any add. Undefined by the problem, but if you handle it, return 0.0 or NaN rather than reading lo.top() on an empty heap.
  • Equality should go to the lower half. num ≤ lo.top(), not <. A new value equal to lo.top() belongs with it, and sending it to the upper half can skew the balance.
  • Rebalance is at most one move. You never move more than one element across. If your rebalance uses a while loop, the invariant was already broken before the add.

7. How to say it in the interview (30 seconds)

"I split the stream into two halves. The lower half is a max-heap, so I can read its biggest in O(1); the upper half is a min-heap, so I can read its smallest in O(1). I keep the max-heap at the same size as the min-heap, or one bigger. On addNum, I push the new value into the correct side (lower if ≤ the lower's root, else upper), then move one element across if the sizes drift out of range. On findMedian, if sizes differ I return the max-heap root; otherwise I average the two roots. O(log n) add, O(1) median. In C++ the min-heap needs the full priority_queue<int, vector<int>, greater<int>> template because the default is max-heap."
