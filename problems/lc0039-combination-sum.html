Combination Sum

LeetCode 39 · Medium · Pattern: backtracking (choose with reuse / skip) · O(NT/min) rough bound, O(T/min) extra space

Problem. Given a list of distinct positive integers candidates and a target target, return every unique multiset of candidates that sums to target. Each number may be reused any number of times. Two multisets are the same if the counts of each number match (order inside a combination does not matter).
candidates = [2,3,6,7], target = 7 → [[2,2,3],[7]]
candidates = [2,3,5], target = 8 → [[2,2,2,2],[2,3,3],[3,5]]
Link: LeetCode

1. The one idea that solves it

Keep the candidates in a fixed order and sweep an index i from left to right. At each index make two decisions: take candidates[i] (and stay at i because reuse is allowed) or skip to i + 1 and never look at candidates[i] again. Track a remain that drops by candidates[i] every time you take.

Two base cases: remain == 0 emits cur; remain < 0 or i == n prunes the branch. Because once you move past i you never come back, no two leaves can describe the same multiset in a different order. That is how uniqueness is enforced without any set.

Idea. Choose/skip over an ordered candidate list, with "choose" keeping i the same so reuse works. Moving the index forward (and never backward) guarantees each multiset is produced in exactly one order, which is how duplicates are avoided.

2. Picture of the algorithm

The recursion at (i, remain) has three outcomes: a hit (remain == 0), a dead end (remain < 0 or ran out of candidates), or branch into two children: take (stay at i) and skip (move to i + 1).

3. Step-by-step trace

The tree below is the full recursion. Each node is a call (i, remain) with the current cur written on top. Left edge = take candidates[i] (cur grows, remain drops, i stays), right edge = skip (i moves on, remain unchanged). Green leaves are hits; red leaves are dead ends.

4. Code (C++)

class Solution {
public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        vector<vector<int>> ans;
        vector<int> cur;
        function<void(int, int)> dfs = [&](int i, int remain) {
            if (remain == 0) { ans.push_back(cur); return; }
            if (i == (int)candidates.size() || remain < 0) return;
            cur.push_back(candidates[i]);                 // take, stay at i (reuse)
            dfs(i, remain - candidates[i]);
            cur.pop_back();                               // unchoose
            dfs(i + 1, remain);                        // skip to next candidate
        };
        dfs(0, target);
        return ans;
    }
};

Complexity: hard to pin exactly; a common bound is O(NT/min) where N is the number of candidates and min is the smallest one, because the deepest "all smallest" chain has T/min takes. Space is O(T/min) for the recursion depth and cur.

Alternative: for-loop form with a start index

void dfs(int start, int remain, vector<int>& c,
         vector<int>& cur, vector<vector<int>>& ans) {
    if (remain == 0) { ans.push_back(cur); return; }
    for (int i = start; i < (int)c.size(); i++) {
        if (c[i] > remain) continue;         // prune (sort first and break for a tighter cut)
        cur.push_back(c[i]);
        dfs(i, remain - c[i], c, cur, ans);  // still allow reuse of c[i]
        cur.pop_back();
    }
}

Same recursion tree with the "skip to i + 1" child baked into the loop's increment. Prefer the for-loop form when you want the natural pruning sort(candidates); if (c[i] > remain) break;, which cuts the tree by an order of magnitude on realistic inputs.

5. The part interviewers ask about: why no duplicates and why "stay at i"

Two subtle points that come up almost every time:

Why uniqueness falls out for free. A combination like [2,2,3] could in theory be built as 2 → 2 → 3 or 3 → 2 → 2. The index i only moves right or stays, so once the recursion has moved past index "2" it will never add another 2. Only the ordered-non-decreasing way of writing a multiset is reachable, so each multiset shows up exactly once.
Why "take" keeps i the same. The problem lets you reuse a number as many times as you want. Keeping i means the next decision is still allowed to take candidates[i] again. Moving to i + 1 after a take would make the algorithm emit combinations with each candidate used at most once (that is actually LC 40 Combination Sum II).

What if there were a duplicate in candidates (LC 40)? You now have both the "no reuse" rule and the risk of two equal candidates producing the same multiset twice. The fix is: sort the array, use the for-loop form, recurse to i + 1 after taking, and at each level if (i > start && c[i] == c[i-1]) continue; to skip equal siblings.

6. Traps and edge cases

  • Recursing to i + 1 after a take. That is LC 40 (no reuse). For LC 39 the recurse must stay at i.
  • Allowing both children at i without an index. If you fan out "pick any candidate" at every level, you will generate every ordering of each multiset and the output will have duplicates.
  • Infinite recursion. If a candidate is 0 and you keep taking, remain never changes. The problem rules out this input (positive candidates), but mention it.
  • Missing the remain < 0 prune. Without sort, you need this check or the recursion will keep adding past the target. With sort plus break, you don't need the explicit check but you still return nothing on that branch.
  • Target already 0. The problem guarantees target ≥ 1, but the base case handles it: emit the empty combination [] and return.

7. How to say it in the interview (30 seconds)

"I use a start index to force each combination into a non-decreasing order of candidate indices. That gives uniqueness for free. At each call I either take the current candidate and recurse at the same index because reuse is allowed, or skip to the next index. The base cases are remain hits zero (emit cur) or remain goes negative / I'm out of candidates (prune). Sorting first lets me break out of the loop as soon as a candidate overshoots, which is the main pruning trick on top of the recursion."
