Merge Intervals

LeetCode 56 · Medium · Pattern: sort by start, sweep · O(n log n) time, O(n) space

Problem. Given a list of intervals [starti, endi], merge all overlapping intervals and return the result.
[[1,3],[2,6],[8,10],[15,18]] → [[1,6],[8,10],[15,18]]
[[1,4],[4,5]] → [[1,5]] (touching endpoints count as overlapping)
Link: LeetCode

1. The one idea that solves it

Sort by start. Then walk left to right. Keep the "current merged interval" as the last pushed one. For every next interval, there are only two cases:

  • It starts before (or at) the current end: they overlap. Stretch the current end to the max of the two ends.
  • It starts after the current end: no overlap. Push it as a new current.

Sorting by start is what makes this one pass sufficient. Once sorted, the only interval that could possibly overlap the one you are looking at is the most recently merged one — everything older is strictly to its left and already closed off.

Idea. After sorting by start, a new interval either extends the current group or starts a new one. One left-to-right pass merges every overlap, because overlapping intervals must be adjacent in sorted order.

Why the greedy choice is safe

Lemma. After sorting by start, any two intervals that overlap are contiguous in sorted order, in the sense that some chain of overlapping neighbours links them — so the walk never "misses" a merge.

Proof sketch (exchange argument). Suppose intervals A and C overlap but between them in sorted order sits B that does not overlap A. Since start times are sorted, A.start ≤ B.start ≤ C.start. "B does not overlap A" means B.start > A.end. But then C.start ≥ B.start > A.end, so C cannot overlap A either — contradicting the assumption. Therefore every chain of overlapping intervals is contiguous in sort order, and a single sweep over the sorted list catches them all.

Why "merge with the previous" always wins. At each step we compare the new interval only with the last merged one. Suppose some earlier merged interval also overlaps the new one. Then it also overlaps the last merged one (by the chain argument above), so it has already been merged into the last one. There is nothing to look back for.

4. Code (C++)

class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {
        sort(intervals.begin(), intervals.end());        // by start, then by end
        vector<vector<int>> out;
        for (auto& iv : intervals) {
            if (!out.empty() && iv[0] <= out.back()[1]) {
                out.back()[1] = max(out.back()[1], iv[1]);  // stretch the end
            } else {
                out.push_back(iv);                       // start a new group
            }
        }
        return out;
    }
};

Complexity: sorting is O(n log n), the sweep is O(n). O(n) space for the output. The sort dominates.

Alternative: sort just the starts and ends separately

vector<vector<int>> merge(vector<vector<int>>& iv) {
    int n = iv.size();
    vector<int> st(n), en(n);
    for (int i = 0; i < n; i++) { st[i] = iv[i][0]; en[i] = iv[i][1]; }
    sort(st.begin(), st.end()); sort(en.begin(), en.end());
    vector<vector<int>> out;
    for (int i = 0, j = 0; i < n; i++)
        if (i == n - 1 || st[i + 1] > en[i])  { out.push_back({st[j], en[i]}); j = i + 1; }
    return out;
}

Decouples starts from ends. Useful when the inputs come as two separate arrays. Same O(n log n).

5. The part interviewers ask about: what if the input is a stream?

If intervals arrive one at a time and you must keep them merged, this exact algorithm is O(n) per insert in the worst case (you may extend the last group, or insert in the middle). A classic follow-up:

Insert Interval (LC 57) — if the existing list is already sorted and merged, inserting one new interval is O(n): walk through, copy the ones strictly before, merge all that overlap into a single stretched interval, then copy the rest. For k inserts into an unordered stream, maintain a balanced BST / std::set keyed by start; each insert finds predecessors/successors in O(log n), merges them, and reinserts. Total O(k log k).

Another good follow-up: why not Union-Find? You could union each pair whose intervals overlap, but detecting "which pairs overlap" without sorting is quadratic. Sort + sweep is strictly simpler. Union-Find helps when the "overlap" relation is given explicitly (edges), not derived from numeric positions.

Open vs closed endpoints. LC 56 treats touching endpoints as overlap ([1,4] and [4,5] merge). If the problem said "open intervals" or "strictly overlap", change ≤ to < in the compare. The algorithm is otherwise identical.

6. Traps and edge cases

  • Sorting by end instead of start. Works for some other interval problems (greedy scheduling, LC 435) but not for merging — the chain argument above relies on start order.
  • Using < instead of ≤. [[1,4],[4,5]] must merge to [1,5]. If you use strict inequality you return two intervals.
  • Using iv[1] for the extended end instead of max(out.back()[1], iv[1]). Breaks on nested intervals like [[1,10],[2,3],[4,5]]: the correct answer is [[1,10]], not [[1,5]].
  • Modifying the input in place without being asked. Sorting intervals mutates the caller's array; mention this in interviews if it is a constraint.
  • Single interval or empty input. The code handles both: an empty input gives an empty output, a single interval gives a one-element output.

7. How to say it in the interview (30 seconds)

"I sort by start, then walk left to right. I keep an output list. For each interval I check only the last pushed one: if the new start is ≤ that end, I stretch the end to the max; otherwise I push the new interval as a new group. One pass covers every merge because sorting by start forces overlapping intervals to be contiguous. O(n log n) time, O(n) output space."
