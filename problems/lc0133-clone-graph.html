Clone Graph

LeetCode 133 · Medium · Pattern: BFS / DFS traversal with a old → new map · O(V + E) time, O(V) space

Problem. Given a reference to a node in a connected, undirected graph, return a deep copy of the whole graph. Each node has an integer val and a list of neighbours. The copy must share no pointers with the original.
adjList = [[2,4],[1,3],[2,4],[1,3]] → a disjoint 4-node square with the same shape
adjList = [[]] → one isolated node    adjList = [] → null
Link: LeetCode

1. The one idea that solves it

A graph has cycles, so a naive "recurse into every neighbour and allocate" loops forever. The fix is a hash map that remembers which original node you have already cloned. Every time you visit a node, look it up in the map: if the clone already exists, use it; if not, allocate the clone and push the original node for later expansion. The map is both the visited set and the pointer bridge from the old world to the new one.

With the map in place, BFS and DFS both work. You can think of it as "trace the original graph, and parallel to each step, wire up the identical edge in the clone".

Idea. Maintain unordered_map<Node*, Node*> clones. Allocate the clone the first time an original is seen; mirror every edge u → v as clones[u] → clones[v]. The map turns the DAG-vs-cycle problem into a one-time-per-node walk.

2. Picture of the algorithm

Why BFS? Because the clone's neighbour list is easier to reason about when all current-node neighbours are wired before you move on. DFS is just as valid; the recursion returns the clone pointer up the call stack, and the map guards against infinite descent. Pick the one you can defend without flinching.

4. Code (C++)

class Solution {
public:
    Node* cloneGraph(Node* node) {
        if (!node) return nullptr;
        unordered_map<Node*, Node*> clones;
        queue<Node*> q;
        clones[node] = new Node(node->val);
        q.push(node);
        while (!q.empty()) {
            Node* u = q.front(); q.pop();
            for (Node* nb : u->neighbors) {
                if (!clones.count(nb)) {
                    clones[nb] = new Node(nb->val);
                    q.push(nb);                            // discover this node
                }
                clones[u]->neighbors.push_back(clones[nb]); // mirror the edge
            }
        }
        return clones[node];
    }
};

Complexity. Each node is pushed and popped once (map guards the push), so the outer work is O(V). The inner loop walks every neighbour, totalling O(2E) work across the whole BFS. So O(V + E) time and O(V) space for the map and the queue.

Alternative: recursive DFS

unordered_map<Node*, Node*> clones;
Node* dfs(Node* u) {
    if (!u) return nullptr;
    if (clones.count(u)) return clones[u];      // bridge back
    Node* c = new Node(u->val);
    clones[u] = c;                                   // insert BEFORE recursing
    for (Node* nb : u->neighbors) c->neighbors.push_back(dfs(nb));
    return c;
}

Same shape, same complexity. The crucial line is clones[u] = c before the recursive call: if you insert after, a cycle makes the recursion infinite. DFS is a little shorter; BFS avoids a tall recursion stack on big graphs.

5. The part interviewers ask about: map keyed by pointer vs. by value

Keys are pointers to the originals, not vals. The problem lets two different nodes carry the same val under the constraints the problem gives (unique vals are a problem-specific comfort, not an algorithmic requirement). Keying on the integer value creates subtle correctness bugs if the same algorithm is reused on a graph with duplicate labels.

Second question: order of the two writes inside the loop. Allocate-then-wire or wire-then-allocate? The code above allocates when the neighbour is seen for the first time, then unconditionally wires an edge from clones[u] to clones[nb]. If you wire before the allocation branch, you must still check-and-insert first; the two statements must not depend on each other's side effects.

Third: why do we not double-wire edges in an undirected graph? Because the problem's adjacency list already stores each undirected edge twice (both endpoints list each other). We mirror whatever the input lists. If an interviewer asks you to normalise to a single-direction edge list, that is a separate pass on the clone, not the clone itself.

6. Traps and edge cases

  • Null input. cloneGraph(nullptr) must return nullptr, not segfault.
  • Isolated node. One node, empty neighbour list: return a new Node(val) with an empty list; the BFS pops it, finds no neighbours, exits.
  • Self-loops. A node that lists itself as a neighbour. The map lookup inside the loop finds the clone and wires it to itself. If you check clones.count(nb) and skip the edge wiring on hit, you lose the self-loop. The code above wires unconditionally after the "discover" branch, so it is correct.
  • Insert into the map AFTER recursing (DFS). On a cycle the second entry into the same original node sees no map entry, allocates again, and recurses forever. Insert before.
  • Mutating the original. Do not touch u->neighbors; only read it. The problem states the original graph is unchanged.
  • Pointer sharing in the output. If any clone's neighbour pointer still points to an original, the copy is shallow. Every neighbour must be looked up through clones.
  • Disconnected graphs. The problem guarantees connectivity. If asked to clone a possibly disconnected graph, wrap the whole algorithm in an outer loop over all nodes.

7. How to say it in the interview (30 seconds)

"I keep an unordered_map from original node pointers to their clones. BFS from the start: pop a node, walk its neighbour list, and for each neighbour, either look up its existing clone or allocate one and enqueue it, then wire an edge in the clone from the current node's clone to the neighbour's clone. The map is both the visited set and the bridge from the old world to the new one. O(V + E) time, O(V) space. The key must be the pointer, not the integer value, so the same code works on graphs with duplicate labels."
