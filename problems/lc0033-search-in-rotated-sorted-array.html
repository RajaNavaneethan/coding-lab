Search in Rotated Sorted Array

LeetCode 33 · Medium · Pattern: binary search with a pivot · O(log n) time, O(1) space

Problem. A sorted array with distinct values was rotated at some pivot you do not know. Given the rotated nums, return the index of target, or -1. Must run in O(log n).
nums = [4,5,6,7,0,1,2], target = 0 → 4    target = 3 → -1
Link: LeetCode

1. The one idea that solves it

Cut the array at any index mid. The pivot sits somewhere, so at least one of the two halves is still sorted end-to-end. You can tell which one by a single comparison:

  • If nums[lo] ≤ nums[mid], the left half [lo..mid] is sorted.
  • Otherwise the right half [mid..hi] is sorted.

Once you know which half is sorted, you can check with two comparisons whether target lies in its range. If yes, keep that half. If no, the target must be in the other half (which contains the pivot). Each step discards half the window, so binary search still runs in log n.

Idea. One of the two halves of [lo..mid..hi] is sorted. Identify it from nums[lo] and nums[mid], then test whether target fits inside that sorted half. Walk into whichever half can still hold it. Everything else is standard binary search.

Why "sorted half" is the right lens

In an unrotated array, "nums[mid] < target" tells you to go right. Here that is not enough: the right half could be [0,1,2] while target = 6 lives on the left. By picking the sorted side first, the range check is unambiguous. The pivot is always in the other half, so if the target is not in the sorted range it must be there.

4. Code (C++)

class Solution {
public:
    int search(vector<int>& nums, int target) {
        int lo = 0, hi = (int)nums.size() - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return mid;
            if (nums[lo] <= nums[mid]) {              // left half sorted
                if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
                else lo = mid + 1;
            } else {                                  // right half sorted
                if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
                else hi = mid - 1;
            }
        }
        return -1;
    }
};

Complexity: each step halves the window, O(log n) time, O(1) space.

5. The part interviewers ask about: why ≤ on the sorted-side test

Writing nums[lo] < nums[mid] breaks when lo == mid (two-cell window): neither half passes the test. Writing nums[lo] ≤ nums[mid] covers that case by declaring the one-element left half sorted (which it trivially is), and the algorithm walks into the correct side.

Similarly, the range check for the sorted half uses ≤ target <: the lower end is inclusive because nums[lo] itself could be the target, the upper end is exclusive because nums[mid] was already compared on line above. Keeping these boundaries clean is what makes the whole thing exact.

Duplicates (LC 81). With duplicates nums[lo] == nums[mid] no longer tells which half is sorted (e.g. [3,1,2,3,3,3,3]). The fix: when nums[lo] == nums[mid], do lo++ and continue. Worst case is O(n), average still O(log n).

// LC 81 variant: handles duplicates
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (nums[mid] == target) return true;
    if (nums[lo] == nums[mid]) { lo++; continue; }   // cannot tell, inch forward
    // then the LC 33 body, unchanged
}

6. Traps and edge cases

  • Comparing nums[mid] with nums[hi] instead of nums[lo]. Also works, but the four boundary cases flip. Pick one anchor and keep it.
  • Using < on the sorted-side test. [3,1], target=1: lo=mid=0 and nums[0] < nums[0] is false, so the code picks the right half, which is right. But swap it to [1,3] (no rotation): mid=0, left half [1,1] is "sorted", target 1 falls inside, we go left and finish. Both arms must handle the one-element case.
  • Not rotated at all. [1,2,3,4,5]: nums[lo] ≤ nums[mid] stays true for every mid, so the algorithm reduces to plain binary search. Good.
  • Pivot exactly at index 0 or n-1. Same as "not rotated" after one or zero spins. No special case.
  • Single element. [1], target = 0: mid = 0, miss, left-half check picks a branch that moves lo or hi, loop exits, return -1.
  • Target equals a boundary. The range check uses inclusive ≤ at the sorted-side ends (nums[lo] or nums[hi]) so the boundary value is caught.

7. How to say it in the interview (30 seconds)

"A rotated sorted array always has at least one sorted half across the middle. I check nums[lo] ≤ nums[mid]: if true, the left half is sorted and I ask whether the target lies in [nums[lo], nums[mid]); otherwise the right half is sorted and I ask about (nums[mid], nums[hi]]. Either way, one half is kept and the other is dropped, so it is O(log n). Watch the ≤ for the two-cell case."
