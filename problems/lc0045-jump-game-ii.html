Jump Game II

LeetCode 45 · Medium · Pattern: BFS-level greedy · O(n) time, O(1) space

Problem. You start at index 0. From index i you can jump to any index in [i+1, i+nums[i]]. Return the minimum number of jumps to reach the last index.
[2,3,1,1,4] → 2    [2,3,0,1,4] → 2
Link: LeetCode

1. The one idea that solves it

Think of the array as a BFS over levels. "Reachable in 0 jumps" is {0}. "Reachable in 1 jump" is every index you can hit from {0}. "Reachable in 2 jumps" is every index you can hit from the level-1 window. And so on. Each level is a contiguous window on the array, because jumps can land anywhere up to i + nums[i].

At level k the window is [l, r]. From every i in that window, the farthest cell you can hit is i + nums[i]. Take the maximum: that is the right edge of level k+1. Its left edge is r + 1. Repeat until the window contains the last index.

Idea. Maintain the current level's window [l, r] and the farthest the next level reaches. When i hits r, we exhaust the current level: increment jumps, advance to the next level.

Why the greedy choice is safe

At each level we care about one number: how far can the next level reach. We never commit to a specific landing cell. Why is "take the farthest reachable" optimal?

Exchange argument. Suppose some optimal plan uses k jumps and lands at index p after k jumps. Let F be the farthest index reachable from the level-k window. By definition p ≤ F. From p you can reach at most p + nums[p] ≤ F + nums[F]? Not quite: it is ≤ F's own reach only after another step. The real claim is weaker and sufficient: any index reachable from p in one more jump is ≤ max over the whole level-k window of (i + nums[i]), which is exactly the new frontier. So replacing the optimal plan's position p after k jumps with "treat every cell up to the new frontier as reachable" never cuts off any later move.

4. Code (C++)

class Solution {
public:
    int jump(vector<int>& nums) {
        int n = nums.size();
        int jumps = 0, curEnd = 0, farthest = 0;
        for (int i = 0; i < n - 1; i++) {        // stop at n-2: nothing to launch from n-1
            farthest = max(farthest, i + nums[i]);  // best next-level frontier
            if (i == curEnd) {                      // finished the current level
                jumps++;
                curEnd = farthest;
            }
        }
        return jumps;
    }
};

Complexity: single pass; each index is read once. O(n) time. Three scalars: O(1) space.

The code looks like it has no window boundaries, but it does: curEnd is the right edge of the current level. The if (i == curEnd) step is the moment we switch levels.

Alternative: explicit windows (easier to explain in an interview)

int jump(vector<int>& nums) {
    int n = nums.size(), jumps = 0, l = 0, r = 0;
    while (r < n - 1) {
        int f = 0;
        for (int i = l; i <= r; i++) f = max(f, i + nums[i]);
        l = r + 1; r = f; jumps++;
    }
    return jumps;
}

Each cell is still touched once total, since levels are disjoint and together they cover [0, n-1). Same O(n).

5. The part interviewers ask about: why not Dijkstra / BFS with a queue?

You could run plain BFS with a queue, treating each index as a node and each legal jump as an edge. That is O(n2) in the worst case: index i can have nums[i] outgoing edges, and sum of nums[i] can be n · max(nums).

The greedy pass is BFS compressed. Because every level is a contiguous window on the array, we can represent an entire level by just (l, r), and the next level's right edge is one max over that window. No queue, no visited set. The "node" is "the whole level", and there are only O(n) levels because every level advances r strictly (otherwise LeetCode's problem guarantees you cannot reach the end).

Correctness: by induction on jump count. After the k-th level update, curEnd equals the farthest index reachable in k jumps. Base: with 0 jumps, curEnd = 0. Step: assume true for k. In the pass over the level-k window, farthest accumulates max(i + nums[i]) over that window, which by definition is the farthest in k+1 jumps. When i reaches curEnd we promote: curEnd ← farthest, jumps++.

6. Traps and edge cases

  • Looping to i < n instead of i < n - 1. The last cell cannot start a new jump; counting it would over-count by one on some inputs.
  • n = 1. Return 0 (already at the end). The i < n - 1 loop handles it: the loop body never runs, so jumps stays 0.
  • Zeros inside a reachable window are harmless. You never land on a zero if a non-zero further in the window reaches past it. LC guarantees the end is reachable, so you do not need a "stuck" check here.
  • Confusing this with Jump Game (LC 55). That one is yes/no reachability; this one counts minimum jumps.
  • Trying to greedily jump to the local maximum of nums[i]. That is wrong. The right measure is i + nums[i], not nums[i]. From [2,3,1,1,4] at i=0, nums[1]=3 looks best, but actually at i=1, 1+3=4 wins — and this problem's greedy correctly maximises reach, not step size.

7. How to say it in the interview (30 seconds)

"I think of it as BFS over levels of reachability. Level k is a contiguous window on the array. I keep the current level's right edge curEnd, and while scanning it I keep farthest, the right edge of the next level. When i hits curEnd, I promote: increment jumps and move curEnd to farthest. I stop at n-2. The greedy is safe because any landing cell within the window has reach bounded by the window's max frontier, so taking the farthest frontier is never worse. O(n) time, O(1) space."
