Subarray Sum Equals K

LeetCode 560 · Medium · Pattern: prefix sum + hash map · O(n) time, O(n) space

Problem. Given an integer array nums (negatives allowed) and an integer k, return how many contiguous subarrays sum to exactly k.
nums = [1,1,1], k = 2 → 2   nums = [1,2,3], k = 3 → 2   Link: LeetCode

1. The one idea that solves it

Let P[j] be the sum of the first j elements. A subarray from index l to r is just the difference of two prefix sums: sum(l..r) = P[r+1] − P[l].

So a subarray ending at the current position sums to k exactly when some earlier prefix sum equals running − k. Each such earlier prefix is a place where you can "cut", and the part after the cut sums to k.

sum(l..r) = k  ⇔  P[l] = P[r+1] − k

That turns the problem into Two Sum on the prefix sums: walk left to right, and at each step ask a hash map "how many earlier prefix sums equal running − k?"

Idea. Keep a running sum and a map from prefix sum to how many times it has occurred. At each element, add count[running − k] to the answer, then record running. Seed the map with {0: 1} so subarrays that start at index 0 are found.

2. Picture of the algorithm

The order inside the loop matters: read first, then write. Writing first would let the current prefix match itself when k = 0, which counts an empty subarray.

3. Step-by-step trace

current element (subarray ends here) a subarray found at this step prefix sum that was matched

4. Code (C++)

int subarraySum(vector<int>& nums, int k) {
    unordered_map<int, int> count{{0, 1}};   // empty prefix seen once
    int running = 0, ans = 0;
    for (int x : nums) {
        running += x;
        auto it = count.find(running - k);
        if (it != count.end()) ans += it->second;   // every earlier cut point is one subarray
        count[running]++;
    }
    return ans;
}

Complexity: one pass with O(1) average hash work per element, so O(n) time. The map can hold up to n+1 distinct prefix sums, so O(n) space.

5. The part interviewers ask about: why not a sliding window?

A sliding window needs one rule: "if the sum is too big, move the left edge right". That only works when every element is positive, because then growing the window always increases the sum and shrinking it always decreases it. With negatives, a too-big window can become exactly right by adding a negative number, so there is no safe shrink rule. The prefix map does not depend on order or sign, so it works for any input. If the interviewer says all numbers are positive, offer the window version: same O(n) time, O(1) space.

Why counts and not a set? With zeros or negatives, the same prefix sum can appear several times. Each occurrence is a different cut point, so each one gives a different subarray. Try [0,0,0], k = 0: the answer is 6, and ans++ instead of ans += it->second returns 3.

6. Traps and edge cases

  • Missing the {0: 1} seed. Every subarray that starts at index 0 is silently missed. [1,2,3], k=3 returns 1 instead of 2.
  • Writing before reading. With k = 0 each prefix matches itself and the count is inflated by n.
  • Using a set, or ans++. Wrong when prefix sums repeat. [0,0,0], k=0 → 6.
  • if (count[running - k]) as the lookup. operator[] inserts a zero entry for every miss. The answer is still right, but the map grows with junk keys. Use find.
  • Overflow. With n = 2·104 and |nums[i]| ≤ 1000 the sum fits in int. Mention long long if the constraints are bigger.
  • Edge inputs. [1], k=0 → 0; [1,-1,0], k=0 → 3; [3,4,7,2,-3,1,4,2], k=7 → 4.

7. How to say it in the interview (30 seconds)

"A subarray sum is the difference of two prefix sums, so a subarray ending here sums to k when some earlier prefix equals the running sum minus k. I walk the array once with a hash map from prefix sum to how often it has appeared, seeded with zero seen once for the empty prefix. At each element I add the count of running minus k, then record the running sum. That's O(n) time and space. A sliding window doesn't work because negative numbers break the shrink rule."
