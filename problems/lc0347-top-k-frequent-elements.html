Top K Frequent Elements

LeetCode 347 · Medium · Pattern: count + size-k min-heap (or bucket sort) · O(n log k) or O(n)

Problem. Given an array nums and an integer k, return the k most frequent elements. The answer may be returned in any order.
[1,1,1,2,2,3], k=2 → [1,2].    [1], k=1 → [1].
Link: LeetCode

1. The one idea that solves it

Reduce the problem to "top-k of a list of (value, frequency) pairs". Count frequencies in one pass with a hash map, then apply the same size-k min-heap trick as LC 215 — but key the heap by frequency. Push every (freq, value) pair; whenever the heap exceeds k, pop the pair with the smallest frequency. What remains is the top-k by frequency.

If the array is dense (many values, each appearing a bounded number of times), there is a bucket sort alternative that runs in O(n) by placing values into buckets indexed by their frequency.

Idea. Count once, then run size-k min-heap on (freq, value) pairs ordered by freq. The heap's root is the least frequent element currently in the top-k, which is exactly the threshold a new pair must beat.

4. Code (C++)

vector<int> topKFrequent(vector<int>& nums, int k) {
    unordered_map<int, int> cnt;
    for (int x : nums) cnt[x]++;                        // O(n) counting

    // min-heap of pair<freq, value>; smallest freq on top
    priority_queue<pair<int,int>,
                   vector<pair<int,int>>,
                   greater<>> pq;
    for (auto& [v, c] : cnt) {
        pq.push({c, v});                               // pair compares by first, then second
        if ((int)pq.size() > k) pq.pop();              // drop current least-frequent
    }

    vector<int> ans;
    while (!pq.empty()) { ans.push_back(pq.top().second); pq.pop(); }
    return ans;                                        // any order allowed
}

Complexity: counting is O(n). The heap holds at most k elements, so each push/pop is O(log k). If there are u unique values, the heap phase is O(u log k) ≤ O(n log k). Space O(n) for the map plus O(k) for the heap.

Why greater<> on pair<int,int> works. std::pair's default comparison is lexicographic: compare first, then second. greater<> flips the order on the first component (frequency), so the heap root is the pair with the smallest frequency. Ties go to the smaller value; that doesn't affect correctness because the problem accepts any order.

Alternative: bucket sort (O(n))

vector<int> topKFrequent(vector<int>& nums, int k) {
    unordered_map<int, int> cnt;
    for (int x : nums) cnt[x]++;
    int n = (int)nums.size();
    vector<vector<int>> buckets(n + 1);                  // buckets[f] = values with frequency f
    for (auto& [v, c] : cnt) buckets[c].push_back(v);
    vector<int> ans;
    for (int f = n; f >= 1 && (int)ans.size() < k; f--)
        for (int v : buckets[f]) {
            ans.push_back(v);
            if ((int)ans.size() == k) break;
        }
    return ans;
}

Why it works: a frequency is at most n, so n+1 buckets suffice. Scanning buckets from high to low collects the most frequent first. O(n) time, O(n) space. Prefer when:

  • You know n up front (bucket sort can't stream).
  • Interviewer asks for strictly O(n) — this beats the heap's O(n log k).

Prefer the heap when: input arrives one element at a time, or when the universe of distinct values is huge but only k matter at any moment.

5. The part interviewers ask about: comparator direction for pair

Everyone can write "min-heap of ints with greater<int>". The subtle one is min-heap of pair<int,int> keyed by frequency. The pair's natural order is (a.first, a.second) lexicographic; passing greater<> as the comparator inverts that order, so the root is the smallest pair — smallest frequency first, with ties broken by smallest value. That is exactly what we need: we want to kick out the least frequent element, so it must sit on top.

If instead you wanted "most frequent on top" (the opposite, size-n max-heap approach), you would use the default priority_queue<pair<int,int>>. That also solves the problem (pop k times) but costs O(n log n) time and O(n) space, which is worse than both alternatives above.

6. Traps and edge cases

  • Pair order matters. Use pair<freq, value>, not pair<value, freq>. Otherwise the heap orders by value, not frequency, and the whole algorithm breaks.
  • Default priority_queue is a max-heap. If you forget greater<>, the heap keeps the most frequent on top and pops them first — you throw away the answer.
  • Pushing then checking size. Push first, then if (size > k) pop. Flipping that order loses one answer.
  • k equals the number of unique values. Then every unique value is in the answer and no pops happen. The code handles this because the size > k check is false.
  • Negative numbers. Values can be any int. The counting map and heap are indifferent; the bucket version uses frequency as the index, not value, so negative values are fine there too.
  • Bucket-sort off-by-one. Buckets are indexed by frequency, which ranges 1..n (not 0..n-1). Size the buckets as n+1 so you can index buckets[n].
  • Returning in sorted order. The problem does not require order, but a careless test harness may compare arrays directly. If you need deterministic order, sort ans at the end.

7. How to say it in the interview (30 seconds)

"I count frequencies in a hash map in O(n). Then I run a size-k min-heap over (frequency, value) pairs: push every pair, pop whenever the heap exceeds k. The pair at the root is the current least-frequent candidate, so popping it keeps the top-k. In C++ I write priority_queue<pair<int,int>, vector<pair<int,int>>, greater<>> — greater flips the lexicographic order of pairs so the smallest frequency is on top. O(n log k) time, O(n) space. If the interviewer asks for linear time, I switch to bucket sort: a vector of n+1 buckets indexed by frequency, scan from high to low until I have k."
