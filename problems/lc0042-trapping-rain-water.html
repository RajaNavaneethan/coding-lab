Trapping Rain Water

LeetCode 42 · Hard · Pattern: two pointers with running max from each side · O(n) time, O(1) space

Problem. height[i] is an elevation at index i, width 1 per bar. After rain, how much water is trapped between the bars?
[0,1,0,2,1,0,1,3,2,1,2,1] → 6    [4,2,0,3,2,5] → 9
Link: LeetCode

1. The one idea that solves it

Think column by column. The water on column i is

water[i] = max(0, min(leftMax[i], rightMax[i]) − height[i])

where leftMax[i] is the tallest bar at or left of i, and rightMax[i] is the tallest bar at or right of i. The limiting wall is the shorter of the two.

Precomputing both arrays is O(n) time and O(n) space. The two-pointer trick cuts the space to O(1): walk from both ends, keep running maxes lmax and rmax, and always advance the side with the smaller height. That side's water depends only on its own running max, so you can commit it right now.

Idea. Two pointers l and r, running maxes lmax and rmax. If height[l] < height[r], then rmax ≥ height[r] > height[l], so min(lmax, rmax) = lmax on column l. Water there is lmax − height[l]. Add it, move l right. Symmetric when height[r] ≤ height[l].

Why the "smaller side" rule is safe

At l, we committed water using lmax. The real cap on column l is min(trueLeftMax, trueRightMax). The left side is correct because lmax is the running max over exactly [0..l]. For the right side we do not know trueRightMax yet, but we know it is at least height[r], which is already greater than height[l]. So min(..., trueRightMax) is pinned by lmax on this column. We never overcount.

4. Code (C++)

class Solution {
public:
    int trap(vector<int>& height) {
        int l = 0, r = (int)height.size() - 1;
        int lmax = 0, rmax = 0, water = 0;
        while (l < r) {
            if (height[l] < height[r]) {
                lmax = max(lmax, height[l]);
                water += lmax - height[l];          // commit left column
                l++;
            } else {
                rmax = max(rmax, height[r]);
                water += rmax - height[r];          // commit right column
                r--;
            }
        }
        return water;
    }
};

Complexity: each pointer moves inward only, so at most n - 1 moves total. O(n) time, O(1) space.

Alternative: precompute leftMax / rightMax arrays

int n = height.size(), water = 0;
vector<int> L(n), R(n);
L[0] = height[0];
for (int i = 1; i < n; i++) L[i] = max(L[i-1], height[i]);
R[n-1] = height[n-1];
for (int i = n-2; i >= 0; i--) R[i] = max(R[i+1], height[i]);
for (int i = 0; i < n; i++) water += min(L[i], R[i]) - height[i];

Three passes, O(n) time, O(n) space. Easier to explain, so write it first in an interview if two pointers do not click. Then compress to the two-pointer version for the O(1)-space finish.

Stack-based alternative

A monotonic decreasing stack of indices also works: each time a taller bar arrives, pop until the stack is empty or the top is taller, adding water for the trapped region. Natural when you also want to answer "largest rectangle" style questions. Still O(n) time, but O(n) space and harder to code quickly.

5. The part interviewers ask about: why not ≤ in the branch?

Compare height[l] < height[r] vs ≤. Equal heights go to the else branch, which commits the right column first using rmax. Both paths give the same answer because when height[l] == height[r], lmax ≥ height[l] == height[r] ≤ rmax, so the water at either column is max(lmax, rmax) − height[?] wait, think again: it is min(lmax, rmax) − h. Here lmax ≥ h[l] and rmax ≥ h[r] == h[l], so neither is below h. Either side's commit is safe. Pick one convention and stick with it.

A deeper correctness point: the invariant maintained each iteration is water above every retired column is already added. The step adds the water above the column it just retired, using a provably correct bound. Retired columns are never revisited, so the final sum is correct.

6. Traps and edge cases

  • Using height[l] itself as the limit instead of lmax. If the current column is taller than the running max, height[l] − height[l] = 0, which is fine, but the formula with lmax is universal. Keep it as lmax − height[l].
  • Updating lmax after adding water. Then the first column of a new rising section looks like it is holding water above itself. Update lmax first, then add.
  • Moving the taller side. You would commit water using a running max that is not actually a safe lower bound on the opposite wall. Move the shorter side.
  • Comparing lmax and rmax instead of height[l] and height[r]. They match once the pointers have crossed every bar, but on step one, both max values start at 0 while the real heights differ. Comparing the heights is what pins the correct side.
  • Monotone input. [1,2,3,4,5] or [5,4,3,2,1] → 0. The pointers walk without ever recording water.
  • Empty / single bar. Loop condition l < r handles both, water = 0.

7. How to say it in the interview (30 seconds)

"Water at column i is min(leftMax, rightMax) − height[i]. The two-pointer trick keeps running maxes from each side and always moves the shorter side inward: on that side the limiting wall is pinned by the local running max, so I can commit water right now. Each pointer walks at most n steps, so O(n) time and O(1) space. The alternative is two prefix-max passes in O(n) space, easier to explain but less tight."
