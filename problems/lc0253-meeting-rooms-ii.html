Meeting Rooms II

LeetCode 253 (Premium) · Medium · Pattern: min-heap of ends / sweep line · O(n log n) time, O(n) space

Problem. Given a list of meeting intervals intervals[i] = [starti, endi], return the minimum number of conference rooms required to hold all meetings. A meeting that ends at time t and another that starts at t can share a room (end is exclusive).
[[0,30],[5,10],[15,20]] → 2
[[7,10],[2,4]] → 1
[[1,5],[5,10]] → 1 (touching ends share a room)
LeetCode 253 is Premium; this problem is also called "Minimum Number of Conference Rooms".

1. The one idea that solves it

At any instant, the number of rooms needed equals the number of meetings currently in progress. The answer is the maximum of this count over all time. Two clean ways to compute that maximum:

  1. Min-heap of end times. Sort meetings by start. Walk through them. The heap tracks "rooms currently in use", each entry is one room's end time. For each new meeting: if the earliest-ending room is already free (heap.top() ≤ start), reuse it; push the new end. At the end, heap.size() is the answer because the heap only ever grows to the peak overlap and never shrinks past it (we only ever push after popping the one freed room).
  2. Sweep line of +1 / −1 events. At every start, +1 room; at every end, −1 room. Sort events (process −1 before +1 at the same time, because touching ends share a room). Running max of the prefix sum is the answer.
Idea. Rooms needed = peak concurrency. Min-heap of end times tracks "which room frees up first"; sweep line counts "how many starts have happened minus how many ends have happened" at every moment. Both give the same answer.

2. Picture of the algorithm

The sweep-line view

Separate every meeting into a +1 start event and a −1 end event, sort by time (end before start on ties), and watch the running sum rise and fall. The peak is the answer.

4. Code (C++)

Main approach: min-heap of end times.

class Solution {
public:
    int minMeetingRooms(vector<vector<int>>& intervals) {
        if (intervals.empty()) return 0;
        sort(intervals.begin(), intervals.end(),
             [](const vector<int>& a, const vector<int>& b){ return a[0] < b[0]; });
        priority_queue<int, vector<int>, greater<int>> busyEnds;  // min-heap
        for (auto& iv : intervals) {
            if (!busyEnds.empty() && busyEnds.top() <= iv[0]) busyEnds.pop();  // reuse a room
            busyEnds.push(iv[1]);
        }
        return (int)busyEnds.size();
    }
};

Complexity: sort is O(n log n), each meeting does O(log n) heap work, total O(n log n). O(n) space for the heap in the worst case (all meetings overlap).

Alternative: sweep line (separate start/end arrays)

int minMeetingRooms(vector<vector<int>>& iv) {
    int n = iv.size();
    vector<int> st(n), en(n);
    for (int i = 0; i < n; i++) { st[i] = iv[i][0]; en[i] = iv[i][1]; }
    sort(st.begin(), st.end()); sort(en.begin(), en.end());
    int rooms = 0, j = 0;
    for (int i = 0; i < n; i++) {
        if (st[i] < en[j]) rooms++;   // a start before the next end: need a new room
        else j++;                     // a room freed up before this start
    }
    return rooms;
}

No heap at all; just two sorted arrays and two pointers. Prefer this when the end-times list is interesting on its own (e.g. you also want to answer "at time T, how many rooms?"). Same O(n log n).

5. The part interviewers ask about

Why is the heap approach correct? If the earliest-freed room (heap.top()) is not free yet, no other busy room is either (its end time is larger). So the only room we could possibly reuse is the top. If it is free we take it; if not we open a new one. The heap never shrinks past the peak overlap because for every pop (reuse) we push once immediately after; the net effect of a reuse is zero change in size, and the net effect of a "no reuse" is +1. Final size = max value size ever reached = peak overlap = minimum rooms.

Why ≤ and not <? A meeting ending at time t and another starting at t can share a room. If we used <, we would wrongly open a second room for [[1,5],[5,10]].

Why sort events "end before start" at ties in the sweep? Same reason: the room is freed at the end time, so at the shared instant the count must first drop (end) and then rise (start). Mix them the other way and touching meetings look like they overlap.

Could we skip sorting and just use counting / difference array? Yes, if time values are small bounded integers: increment d[start], decrement d[end], prefix sum, take max. O(T + n) where T is the time range. Great when times are small, bad when they can be up to 109.

6. Traps and edge cases

  • Using < instead of ≤ in heap.top() ≤ start. Wrong on [[1,5],[5,10]] (should be 1 room).
  • Max-heap instead of min-heap. You need the earliest-ending room, not the latest.
  • Forgetting to sort meetings by start. The heap logic depends on seeing meetings in start order; without it a late-starting meeting could claim a room that is not yet free.
  • Sweep-line tie-break reversed. Mixing start before end at equal time breaks the shared-room rule. Explicit tie: sort pairs (time, kind) with kind=0 for end, kind=1 for start.
  • Empty input. Return 0.
  • Single meeting. Return 1.
  • Returning max(size) during the loop vs size at the end. Both work for the heap version because we only pop before pushing, so size is monotone until the pop-then-push pattern; the final size equals the maximum.

7. How to say it in the interview (30 seconds)

"Rooms needed is just peak concurrency. I sort meetings by start and run a min-heap of end times for rooms currently in use. For each meeting I check the earliest-freeing room: if its end is ≤ this start I pop it (reuse that room); either way I push this meeting's end. The final heap size is the answer. The alternative is a sweep line of +1/−1 events sorted by time with ends tied before starts, and track the running max."
