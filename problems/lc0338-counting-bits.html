Counting Bits

LeetCode 338 · Easy · Pattern: DP on bits (i >> 1 subproblem) · O(n) time, O(n) space for output

Problem. For an integer n, return an array ans of length n + 1 where ans[i] is the number of 1 bits in the binary representation of i.
n = 2 → [0,1,1]    n = 5 → [0,1,1,2,1,2]
Link: LeetCode

1. The one idea that solves it

Chop off the last bit. The number i in binary is the number i >> 1 with one extra bit on the right, and that extra bit is i & 1. So:

popcount(i) = popcount(i >> 1) + (i & 1)

The right-shift value i >> 1 is always smaller than i, so by the time you reach i you have already computed its answer. One DP table, filled from left to right, each cell is one shift plus one AND plus one add.

Idea. The popcount of i is the popcount of i with its last bit removed, plus one if that last bit was a 1. Store popcounts in order and read the i >> 1 cell to compute cell i.

2. Picture of the algorithm

Running popcount per index with Brian Kernighan or __builtin_popcount is O(n log n) in the worst case and does not use the structure between indices. The DP trades that for pure O(n).

4. Code (C++)

class Solution {
public:
    vector<int> countBits(int n) {
        vector<int> dp(n + 1, 0);
        for (int i = 1; i <= n; i++)
            dp[i] = dp[i >> 1] + (i & 1);
        return dp;
    }
};

Complexity: one pass, O(1) work per index: O(n) time. The output is O(n) by definition; no extra space beyond it.

Alternative: lowest-bit recurrence

vector<int> countBits(int n) {
    vector<int> dp(n + 1, 0);
    for (int i = 1; i <= n; i++)
        dp[i] = dp[i & (i - 1)] + 1;    // drop the lowest set bit
    return dp;
}

Same O(n), different recurrence. It uses i & (i − 1) (the Kernighan trick from LC 191) to find a subproblem that is strictly smaller. The i >> 1 form is a hair faster in practice because the shift and AND can be folded by the compiler, but both are correct and both are fine to mention.

5. The part interviewers ask about: why this is DP and not just popcount in a loop

You can call __builtin_popcount(i) for each i and finish in O(n) too, because that intrinsic is one CPU instruction on modern hardware. The interview question is testing a different muscle: can you spot the recurrence between the answers? That is what unlocks follow-ups like "do it without any builtin" and "do it in one pass with no multiplication, no division, no modulo".

Every integer i > 0 can be split as "i >> 1 shifted left by one, with i & 1 added back". That split means popcount(i) never depends on anything other than one cell to its left in the DP table, and you fill left to right.

If asked to prove the recurrence: let bkbk−1…b1b0 be the binary form of i. Then i >> 1 = bkbk−1…b1, dropping the last bit. The popcount of the shifted number is the popcount of i minus b0, and b0 = i & 1. Rearrange and you have the recurrence.

6. Traps and edge cases

  • n = 0. The result is [0]. The loop body never runs, which is correct.
  • Allocating n instead of n + 1. You need indices 0..n inclusive, so the vector has length n + 1. Off-by-one here is the most common bug.
  • Writing i & 1 as i % 2. They agree for non-negative i, which is all this problem uses, so this is only a style and a tiny-perf nit, not a correctness bug.
  • Trying to use dp[i / 2] as the source but then mixing in signed negatives. This problem guarantees 0 ≤ n ≤ 105, so this is theoretical. On signed negatives, i >> 1 is implementation-defined before C++20 (usually arithmetic shift), while i / 2 truncates toward zero, so they disagree.
  • Thinking you must sort by popcount or iterate bit by bit. You don't. Index order i = 1..n already visits every i >> 1 before i.

7. How to say it in the interview (30 seconds)

"Chop off the lowest bit. i has one more bit than i >> 1, and that extra bit is i & 1. So dp[i] = dp[i >> 1] + (i & 1). Fill left to right from dp[0] = 0. One shift, one AND, one add per cell. O(n) time and no extra space beyond the output. An equivalent recurrence drops the lowest set bit instead: dp[i] = dp[i & (i − 1)] + 1."
