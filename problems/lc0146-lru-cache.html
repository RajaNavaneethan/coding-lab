LRU Cache

LeetCode 146 · Medium · Pattern: hash map + doubly linked list · O(1) get and put

Problem. Design a cache with fixed capacity. Support get(key) (return the value, or -1 if missing) and put(key, value) (insert or overwrite). Both operations must run in O(1). When put would overflow the cache, evict the least recently used key.
Link: LeetCode

1. The one idea that solves it

Two separate things need to be fast:

  1. Find a key's value by key. A hash map does this in O(1).
  2. Track recency, so eviction knows which key is oldest. A doubly linked list where "most recent" lives at the head and "least recent" at the tail does this in O(1) if you can move a known node to the head and delete the tail.

So keep both. The hash map stores key → pointer to the list node that holds (key, value), so a get can find the node and move it to the head in O(1). The doubly linked list's prev-pointers are what make the move O(1): to remove a node, you need its neighbours, and only a doubly linked list hands them to you without walking.

Idea. Hash map answers "where is key k?" in O(1). Doubly linked list orders nodes by recency so the LRU node is always at the tail. Every operation touches a constant number of pointers.

2. Picture of the algorithm

Two sentinel nodes (head and tail) sit at the ends of the list and are never real cache entries. They remove every null check: head->next is the most recent real node, tail->prev is the least recent, and both exist on an empty cache (they just point at each other).

4. Code (C++)

class LRUCache {
    struct Node {
        int key, val;
        Node *prev, *next;
        Node(int k, int v) : key(k), val(v), prev(nullptr), next(nullptr) {}
    };
    int cap;
    Node *head, *tail;                      // sentinels; head->next = MRU, tail->prev = LRU
    unordered_map<int, Node*> mp;

    void unlink(Node* n) {              // detach n from wherever it is
        n->prev->next = n->next;
        n->next->prev = n->prev;
    }
    void pushFront(Node* n) {           // insert n right after head
        n->next = head->next;
        n->prev = head;
        head->next->prev = n;
        head->next = n;
    }

public:
    LRUCache(int capacity) : cap(capacity) {
        head = new Node(0, 0);
        tail = new Node(0, 0);
        head->next = tail;
        tail->prev = head;
    }
    int get(int key) {
        auto it = mp.find(key);
        if (it == mp.end()) return -1;
        unlink(it->second);
        pushFront(it->second);              // mark as most recently used
        return it->second->val;
    }
    void put(int key, int value) {
        auto it = mp.find(key);
        if (it != mp.end()) {               // overwrite + move to front
            it->second->val = value;
            unlink(it->second);
            pushFront(it->second);
            return;
        }
        if ((int)mp.size() == cap) {       // evict LRU
            Node* lru = tail->prev;
            unlink(lru);
            mp.erase(lru->key);
            delete lru;
        }
        Node* n = new Node(key, value);
        pushFront(n);
        mp[key] = n;
    }
};

Complexity: unordered_map gives O(1) average lookup/insert/erase. Every list operation (unlink, pushFront) touches four pointers, so O(1) worst case. Total: O(1) per op, O(capacity) space.

Alternative: std::list + iterator in the map

class LRUCache {
    int cap;
    list<pair<int, int>> dq;                                      // front = MRU
    unordered_map<int, list<pair<int, int>>::iterator> mp;
public:
    LRUCache(int c) : cap(c) {}
    int get(int k) {
        auto it = mp.find(k);
        if (it == mp.end()) return -1;
        dq.splice(dq.begin(), dq, it->second);
        return it->second->second;
    }
    void put(int k, int v) {
        auto it = mp.find(k);
        if (it != mp.end()) {
            it->second->second = v;
            dq.splice(dq.begin(), dq, it->second);
            return;
        }
        if ((int)dq.size() == cap) {
            mp.erase(dq.back().first);
            dq.pop_back();
        }
        dq.push_front({k, v});
        mp[k] = dq.begin();
    }
};

Prefer when the interviewer is happy with STL. list::splice moves one node in O(1) without invalidating iterators, which is why the map stores iterators (not nodes). Behaviour is identical to the hand-rolled version; the hand-rolled version is a stronger interview answer because it proves you understand the pointer bookkeeping.

5. The part interviewers ask about: three design choices

  • Why doubly linked list? To move a known node to the head in O(1), you must remove it from its current spot in O(1), and that needs its predecessor. A singly linked list would force an O(n) walk.
  • Why store the key inside the node (not just the value)? When eviction fires, you learn which node to drop (the tail's prev) but still need to erase its entry from the hash map. The map key must come from somewhere — store it on the node.
  • Why sentinels? They turn every unlink/pushFront into unconditional pointer updates. Without sentinels, both methods need extra ifs for empty list, inserting at head, deleting the only node, deleting the head/tail. More branches, more bugs.

A classic follow-up: is LRU the "right" eviction policy? It's the right answer here because the problem asks for it, but production caches often use LFU (least frequently used), LRU-K, or an admission filter (TinyLFU) because pure LRU can be fooled by a single scan that evicts hot data. Mentioning this shows you've thought past the problem statement.

A second follow-up: what if we allow concurrent access? The map and the list share state, so you need a single lock around the whole op (segmented locks don't help because every op touches recency). Lock-free LRU is a research-grade problem.

6. Traps and edge cases

  • Erasing from the map by iterator before the delete. On the eviction path, read lru->key first, then unlink/erase/delete, in that order. If you delete lru before mp.erase(lru->key), the key read is a use-after-free.
  • Forgetting to move on get. A naive implementation only reorders on put. Then recently-read keys count as "old" and get evicted first.
  • Overwrite on put. Must update value and move to the head. If you leave the node where it is, recency is wrong.
  • Evicting when the key already exists. On an overwrite, do not evict. You're not adding a new entry.
  • Capacity 0. Degenerate: every put instantly evicts; every get returns -1. Keep the code general; the eviction branch handles it.
  • Returning the value then moving the node. Fine as long as the node still exists. Just make sure you don't read from it->second after an erase.
  • Singly linked list "optimisation". Someone will suggest removing the prev pointer. It breaks O(1) unlink; don't accept it.

7. How to say it in the interview (30 seconds)

"I use a hash map keyed by key, mapping to a node in a doubly linked list that stores (key, value). The list is ordered by recency: head-side is most recently used, tail-side is least. On get, I look up the node in the map and move it to the head. On put for an existing key, I update the value and move it to the head. On put for a new key, if the cache is full I remove the node at the tail and erase its key from the map, then insert the new node at the head. I use two sentinel nodes so the list operations never need null checks. All operations touch a constant number of pointers, so O(1) each."
