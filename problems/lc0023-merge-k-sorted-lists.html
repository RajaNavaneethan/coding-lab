Merge k Sorted Lists

LeetCode 23 · Hard · Pattern: min-heap of list heads · O(N log k) time, O(k) space

Problem. You are given an array of k sorted linked lists. Merge them into a single sorted linked list and return its head. Let N be the total number of nodes.
[[1,4,5],[1,3,4],[2,6]] → [1,1,2,3,4,4,5,6].    Link: LeetCode

1. The one idea that solves it

At every step of the output, the next node is the smallest value currently sitting at the head of any input list. If you can find that smallest head in O(log k), each of the N nodes costs O(log k) to place, and the total is O(N log k).

A min-heap keyed by the node's val gives you exactly that. Seed the heap with every non-empty list's head. Repeatedly pop the smallest, splice it to the output tail, and — crucially — push its next back into the heap. The heap always contains at most k nodes (one per input list), so push/pop is O(log k).

Idea. The heap stores one representative per input list: the current head. Pop the overall minimum, link it to the output, then push that node's successor from the same list. Lists that run out simply stop contributing.

4. Code (C++)

ListNode* mergeKLists(vector<ListNode*>& lists) {
    // min-heap on node value; a is "bigger" when its val is bigger
    auto cmp = [](ListNode* a, ListNode* b) { return a->val > b->val; };
    priority_queue<ListNode*, vector<ListNode*>, decltype(cmp)> pq(cmp);

    for (ListNode* h : lists) if (h) pq.push(h);     // seed: one head per non-empty list

    ListNode dummy(0);
    ListNode* tail = &dummy;
    while (!pq.empty()) {
        ListNode* n = pq.top(); pq.pop();                  // smallest head overall
        tail->next = n; tail = n;                          // splice into output
        if (n->next) pq.push(n->next);                      // advance that list
    }
    return dummy.next;
}

Complexity: each of the N nodes gets pushed once and popped once. Each heap op is O(log k) because the heap size is bounded by k. Total O(N log k) time, O(k) extra space.

About the comparator direction. priority_queue's "top" is whatever the comparator calls largest. The default comparator less<T> (a < b) gives you a max-heap. To get a min-heap you pass a comparator that returns true when a should sit below b in the final order — i.e. a comparator that behaves like greater. For custom types the lambda return a->val > b->val is the exact min-heap recipe: it tells the heap "a is bigger than b when a's value is bigger", so the smallest value lands at the top.

Alternative: pairwise merge (divide and conquer)

ListNode* mergeTwo(ListNode* a, ListNode* b) {
    ListNode dummy(0); ListNode* t = &dummy;
    while (a && b) {
        if (a->val <= b->val) { t->next = a; a = a->next; }
        else                  { t->next = b; b = b->next; }
        t = t->next;
    }
    t->next = a ? a : b;
    return dummy.next;
}
ListNode* mergeKLists(vector<ListNode*>& lists) {
    if (lists.empty()) return nullptr;
    while (lists.size() > 1) {
        vector<ListNode*> merged;
        for (size_t i = 0; i < lists.size(); i += 2)
            merged.push_back(i + 1 < lists.size()
                             ? mergeTwo(lists[i], lists[i + 1])
                             : lists[i]);
        lists = merged;
    }
    return lists[0];
}

Same O(N log k) time, no heap. Each round halves the number of lists, and the total work per round is O(N), across log k rounds. Prefer when the interviewer wants to see merge-sort structure or when STL priority_queue isn't available. The heap version wins when lists arrive incrementally or when you want simpler code.

5. The part interviewers ask about: why "push next" is the whole algorithm

The heap is a moving front, not a snapshot. Every time a node leaves (popped), the next node from its list takes its place in the heap. That one line — if (n->next) pq.push(n->next) — keeps the invariant "heap contains the current head of every still-non-empty list". If you forget it, you only ever output the k original heads and then stop.

A natural follow-up: why not put all N nodes into a heap at once? You can, but then each op is O(log N) instead of O(log k) and space is O(N). Keeping only one per list is strictly cheaper when k << N.

Another follow-up: stability. Ties are broken by whichever list's head reached the top of the heap first, which is implementation-defined. If stability by input order matters, extend the heap key to pair<int, int> of (val, list_index).

6. Traps and edge cases

  • Null lists in the input. Skip them when seeding. Pushing nullptr and later dereferencing a->val inside the comparator crashes.
  • Forgetting pq.push(n->next). You only output k nodes (the originals) and the result is wrong.
  • Comparator pointing the wrong way. a->val < b->val yields a max-heap on values, so you keep extracting the largest head: output comes out backwards and wrong. Must be >.
  • Using std::less<T> and expecting a min-heap. Default less gives a max-heap for priority_queue. Pass a comparator that behaves like greater.
  • Advancing tail but not resetting n->next. It's fine to leave n->next alone because the next assignment to tail->next overwrites it. Just make sure the last popped node ends with next = nullptr. The simplest route: when the loop ends, set tail->next = nullptr. The code above gets away without it because the last node's original next is already nullptr (we popped it precisely because it had none to push).
  • Empty input lists. Loop never runs; dummy.next is nullptr. Correct.
  • Memory ownership. We reuse the given nodes; no new calls. Don't delete the dummy — it is stack-allocated.

7. How to say it in the interview (30 seconds)

"I keep a min-heap of the current head of each list. I seed it with every non-null list head. Then I repeatedly pop the smallest node, link it to the output tail, and push that node's next back into the heap. Lists that run out stop contributing. The heap holds at most k nodes, so each push and pop is O(log k); every one of the N nodes goes through once, so total time is O(N log k) and extra space is O(k). In C++ I write the comparator as return a->val > b->val — priority_queue's default is a max-heap, so a comparator that behaves like greater inverts it to a min-heap."
