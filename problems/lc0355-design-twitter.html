Design Twitter

LeetCode 355 · Medium · Pattern: Design / k-way merge with a heap · O(1) post, O((k+10) log k) feed

Problem. Design a tiny Twitter with four operations:
  • postTweet(user, tweetId) — user composes a tweet.
  • getNewsFeed(user) — return the 10 most recent tweet IDs from the user plus everyone they follow, newest first.
  • follow(followerId, followeeId)
  • unfollow(followerId, followeeId)
Link: LeetCode

1. The one idea that solves it

Keep each user's own tweets in a per-user list, in chronological order. For a feed, we want the newest 10 across several such lists — each list is already sorted by time, so this is the classic k-way merge of sorted lists: pour the tails into a max-heap keyed on timestamp, pop the newest, then push the next-older tweet from the same list. Stop after 10 pops.

A single global timestamp counter clk that we bump on every post gives us the ordering key for free. No real clocks, no ties.

Membership (follow / unfollow) is just a hash set per user. The follower is always included in their own feed, even if they don't explicitly follow themselves.

Idea. Store tweets per user in time order. A feed is a k-way merge over the follower's own list plus the lists of everyone they follow — max-heap on (timestamp, tweetId, userId, indexInTheirList), pop 10.

2. Picture of the algorithm

Alternative shapes exist (merge everyone's tweets into a single global list, or a global heap of size 10). The k-way merge is the clean choice because it keeps post O(1) and only pays O((k+10) log k) at feed time, where k is the number of followees. The merge is also exactly what interviewers want to see — it generalises to distributed timelines.

4. Code (C++)

class Twitter {
    int clk = 0;                                  // global timestamp
    unordered_map<int, vector<pair<int,int>>> tweets;  // user -> (time, tweetId), chronological
    unordered_map<int, unordered_set<int>> follows;         // user -> set of followees

public:
    Twitter() {}

    void postTweet(int userId, int tweetId) {
        tweets[userId].push_back({++clk, tweetId});
    }

    vector<int> getNewsFeed(int userId) {
        // k-way merge of the newest tails from each feed source.
        // Max-heap of (time, tweetId, ownerId, indexIntoTheirList).
        using Node = tuple<int,int,int,int>;
        priority_queue<Node> pq;
        auto push_last = [&](int u) {
            auto it = tweets.find(u);
            if (it == tweets.end() || it->second.empty()) return;
            int idx = (int)it->second.size() - 1;
            pq.push({it->second[idx].first, it->second[idx].second, u, idx});
        };
        push_last(userId);
        for (int f : follows[userId]) if (f != userId) push_last(f);
        vector<int> out;
        while (!pq.empty() && (int)out.size() < 10) {
            auto [t, id, u, idx] = pq.top(); pq.pop();
            out.push_back(id);
            if (idx > 0) {
                auto& v = tweets[u];
                pq.push({v[idx-1].first, v[idx-1].second, u, idx-1});
            }
        }
        return out;
    }

    void follow(int followerId, int followeeId) {
        if (followerId != followeeId) follows[followerId].insert(followeeId);
    }

    void unfollow(int followerId, int followeeId) {
        auto it = follows.find(followerId);
        if (it != follows.end()) it->second.erase(followeeId);
    }
};

Complexity. postTweet is O(1) amortised. follow/unfollow are O(1). getNewsFeed seeds the heap with up to k entries (one per feed source), then pops at most 10 times with up to 10 pushes — O((k + 10) log k) time, O(k) extra space.

Alternative: scan everyone's full list and sort

vector<pair<int, int>> buf;
for (int u : feedSources(userId))
    for (auto& [t, id] : tweets[u]) buf.push_back({t, id});
sort(buf.rbegin(), buf.rend());
buf.resize(min(10, (int)buf.size()));

Dead simple. Prefer when a user may follow many people but each has only a handful of tweets, or when "feed length" isn't fixed. The heap version wins when any user can have a very long tweet history: the heap only touches the newest tail of each list.

5. The part interviewers ask about: why k-way merge is the right shape

  • Each user's list is already sorted by time. We never need to re-sort. Only the pointers into the tails need to be managed, and that's exactly what a heap does.
  • Heap pops are bounded by 10, not by total tweets. If a user you follow has posted a million tweets, we touch only the newest 10 of them in the worst case, not a million.
  • A global list across all users would also work but you'd have to filter down to the follower's sources on every feed, which is O(global tweets). Per-user lists keep the work proportional to what the viewer sees.
  • Followers always include themselves. Call push_last(userId) unconditionally in getNewsFeed, independent of follows[userId]. Interviewers love asking "what if a user follows themselves?" — our guard if (followerId != followeeId) keeps the follow set clean, and we add the self source explicitly so the feed is right either way.

6. Traps and edge cases

  • Forgetting the self-source. If you only merge follows[userId] you miss the user's own tweets. The reference solution always pushes the user themselves.
  • Comparator direction. C++'s priority_queue is a max-heap by default, which is what we want on the first element of the tuple (timestamp). If you reach for greater<> or a custom comparator, get the direction right — it is a classic bug.
  • Duplicate tweet IDs. Not forbidden. The timestamp disambiguates ordering, so the heap never ties.
  • Unfollow something you don't follow. No crash: erase on a missing key is a no-op.
  • Follow or unfollow a user who has never tweeted. No crash: tweets[u] would be absent; our push_last checks the iterator before dereferencing.
  • Mutation during iteration. If you ever decide to filter or expire tweets inside getNewsFeed, don't mutate the user's list — copies are cheap because we only look at the tail.
  • Order within the same timestamp. Can't happen with a single-threaded clk that increments before each insert. If you later go concurrent, use (clk++, tweetId) as the key: still unique.

7. How to say it in the interview (30 seconds)

"I keep two maps. tweets[user] is a chronological list of (timestamp, tweetId), and follows[user] is a hash set of followees. A global counter stamps every post. For getNewsFeed, I seed a max-heap with the newest tweet of each feed source (the user themselves plus everyone they follow), pop the top, and push the next-older one from the same user. Ten pops gives the feed. Post is O(1); feed is O((k+10) log k) in the number of followees. The trick is the k-way merge: each per-user list is already sorted, so we never re-sort anything."
