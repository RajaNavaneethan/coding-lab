Reverse Linked List

LeetCode 206 · Easy · Pattern: in-place pointer rewiring · O(n) time, O(1) space

Problem. Given the head of a singly linked list, reverse it and return the new head.
1 → 2 → 3 → 4 → 5 becomes 5 → 4 → 3 → 2 → 1. Link: LeetCode

1. The one idea that solves it

Walk the list once and flip each arrow as you pass it. The only trick is that flipping curr->next loses the way forward, so save the next node first.

Three pointers run together: prev is the already-reversed part behind you, curr is the node whose arrow you flip this step, and next is the saved successor so you can walk on.

Idea. Keep three pointers. Each step: remember next = curr->next, point curr->next back at prev, then slide the window forward (prev = curr, curr = next). After the walk, prev is the new head.

2. Picture of the algorithm

Nothing shrinks or branches. Each node is visited exactly once and gets its arrow rewritten. When curr walks off the end (becomes null), prev sits on what used to be the tail, which is now the new head.

3. Step-by-step trace

prev (already reversed) curr (flip this) next (saved) not yet touched

4. Code (C++)

ListNode* reverseList(ListNode* head) {
    ListNode* prev = nullptr;
    ListNode* curr = head;
    while (curr) {
        ListNode* next = curr->next;   // save: the flip overwrites it
        curr->next = prev;             // flip this arrow
        prev = curr;                   // slide the window
        curr = next;
    }
    return prev;                     // prev is the old tail = new head
}

Complexity: one pass over n nodes, constant work per node, no extra storage. O(n) time, O(1) space.

Alternative: recursive

ListNode* reverseList(ListNode* head) {
    if (!head || !head->next) return head;
    ListNode* newHead = reverseList(head->next);
    head->next->next = head;      // the next node now points back to me
    head->next = nullptr;         // I become the new tail
    return newHead;
}

Prefer when the interviewer asks for a recursive solution. Same O(n) time but O(n) stack space, which is a real downside on a long list (stack overflow on 105 nodes). The iterative version is the default answer.

5. The part interviewers ask about: why the order of the three lines matters

Three statements inside the loop, and swapping any two breaks the algorithm. Reason it through on paper:
  • If you flip curr->next = prev before saving next, the way forward is gone and the loop never terminates (or you walk a now-reversed arrow and loop back to prev).
  • If you slide prev = curr before the flip, you flip curr->next to curr itself and build a one-node self-loop.
The order save, flip, slide prev, slide curr is the only one that works.

A short invariant pins the correctness: at the top of each iteration, prev heads the already-reversed prefix and curr heads the still-original suffix. The body preserves that invariant for one more node. When curr == nullptr, the suffix is empty and prev is the full reversed list.

6. Traps and edge cases

  • Empty list. head == nullptr → the loop body never runs, prev stays nullptr, which is the correct answer.
  • Single node. First iteration saves next = nullptr, flips the (already null) arrow to nullptr, and the loop exits. Head unchanged, which is correct.
  • Forgetting to null the tail. In the recursive version, if you don't set head->next = nullptr, the reversed list ends in a two-cycle between the first and second nodes.
  • Returning head instead of prev. head is now the tail. Common mistake under time pressure.
  • Using curr->next after the flip. Trying to read curr->next on the next line gives you prev instead of the real successor.

7. How to say it in the interview (30 seconds)

"Three pointers: prev, curr, next. For each node I save its successor into next, flip its arrow to point at prev, then move the window forward by setting prev = curr and curr = next. When curr is null I return prev, which is the old tail. One pass, no extra memory. The recursive version is one line shorter but costs O(n) stack."
