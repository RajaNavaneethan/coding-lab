Non-overlapping Intervals

LeetCode 435 · Medium · Pattern: greedy, sort by end · O(n log n) time, O(1) extra space

Problem. Given a list of intervals, return the minimum number you must remove so that the rest are pairwise non-overlapping. Touching endpoints ([1,2] and [2,3]) do not overlap.
[[1,2],[2,3],[3,4],[1,3]] → 1 (remove [1,3])
[[1,2],[1,2],[1,2]] → 2
[[1,2],[2,3]] → 0
Link: LeetCode

1. The one idea that solves it

Flip the problem: instead of counting what to remove, count the maximum number you can keep such that none overlap, then answer is n − kept. This is the classic activity selection problem.

Greedy rule: sort by end. Walk left to right. Keep the first interval. For every next one, keep it if its start is ≥ the last kept interval's end; otherwise drop it.

Sorting by end is what makes the greedy correct. The interval that ends earliest leaves the biggest tail of the number line still available, so picking it first can never hurt the final count. Sorting by start does not work: a long interval starting early can block many short intervals that would otherwise all fit.

Idea. Keep as many as possible by always picking the compatible interval that ends earliest. Removed count = n − kept. Sort by end, then one left-to-right sweep.

Why sort by end is the right greedy

Exchange argument. Let G be the greedy answer and O any optimal answer, both written in order. Compare them left to right. At the first index where they differ, G picked some interval g and O picked o. By construction g.end ≤ o.end (greedy picks the earliest-ending compatible interval). Swap o for g in O: everything to the right of o in O starts at or after o.end ≥ g.end, so it is still compatible with g. The modified O has the same size as the original and now agrees with G one slot further. Repeat the swap and G itself is optimal.

Why sort-by-start fails. Take [[1,100],[11,12],[12,13]]. Sort by start: keep [1,100], drop the other two. Answer says remove 2. Correct answer: keep [11,12] and [12,13], remove only 1.

4. Code (C++)

class Solution {
public:
    int eraseOverlapIntervals(vector<vector<int>>& intervals) {
        if (intervals.empty()) return 0;
        sort(intervals.begin(), intervals.end(),
             [](const vector<int>& a, const vector<int>& b){ return a[1] < b[1]; });
        int removed = 0;
        int lastEnd = intervals[0][1];
        for (int i = 1; i < (int)intervals.size(); i++) {
            if (intervals[i][0] < lastEnd) {
                removed++;                     // overlaps the kept one; drop it
            } else {
                lastEnd = intervals[i][1]; // disjoint; keep it, slide the window right
            }
        }
        return removed;
    }
};

Complexity: O(n log n) for the sort, O(n) for the sweep, O(1) extra space (ignoring the sort's). The sort dominates.

Alternative: count kept, then subtract

int eraseOverlapIntervals(vector<vector<int>>& iv) {
    sort(iv.begin(), iv.end(), [](auto& a, auto& b){ return a[1] < b[1]; });
    int kept = 0, lastEnd = INT_MIN;
    for (auto& it : iv) if (it[0] >= lastEnd) { kept++; lastEnd = it[1]; }
    return iv.size() - kept;
}

Same algorithm, cleaner initialisation using INT_MIN as a sentinel. Useful when you also want the kept set itself (interview follow-up: "which ones do you keep?").

5. The part interviewers ask about

This IS activity selection. Think of each interval as a meeting with a fixed room. "How many non-overlapping meetings can one room host?" is answered by earliest-finish-time greedy. LC 435 is the same problem turned inside out: remove the smallest number of meetings so the room is never double-booked.

Weighted version? If each interval had a value and you wanted the max total value of a non-overlapping subset, greedy fails. Use DP sorted by end: dp[i] = max(dp[i-1], value[i] + dp[prev(i)]), where prev(i) is the largest index whose end is ≤ intervals[i].start, found by binary search. O(n log n). This is LC 1235 Maximum Profit in Job Scheduling.

Touching endpoints. LC 435 says touching is not overlap, so compare with < (start < lastEnd means overlap). If the variant said "closed intervals, touching overlaps", switch to ≤.

6. Traps and edge cases

  • Sorting by start. Fails on [[1,100],[11,22],[1,11],[2,12]]. Correct answer 2; sort-by-start pick-first gives 3.
  • Using ≤ instead of < in the overlap check. LC 435 explicitly says [1,2] and [2,3] do not overlap. Strict inequality is required.
  • Keeping the longer interval on a tie. When two intervals end at the same time, sorting by end alone can put either first. It does not matter which: both have the same end, so the walk makes the same subsequent choices.
  • Empty input. Return 0.
  • All intervals identical. Keep one, remove the rest → n − 1.
  • Updating lastEnd on a dropped interval. Do not. The dropped interval has an end ≥ lastEnd (because sort is by end), so updating would wrongly extend the barrier and lose future keeps.

7. How to say it in the interview (30 seconds)

"I flip the problem: maximise what I keep. Sort by end. Walk left to right. Keep the first interval. For each next one, if its start is at least the last kept end, keep it and update lastEnd; otherwise count a removal. Answer is removals, or n − kept. The exchange argument says earliest-finish-time is optimal because it leaves the biggest tail of the number line free. O(n log n)."
