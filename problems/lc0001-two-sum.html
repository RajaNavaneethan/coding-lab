Two Sum

LeetCode 1 · Easy · Pattern: hash map lookup (unsorted) · O(n) time, O(n) space

Problem. Given nums and target, return the indices of the two numbers that add up to target. Exactly one answer. You cannot use the same element twice.
[2,7,11,15], 9 → [0,1]    [3,2,4], 6 → [1,2]    [3,3], 6 → [0,1]
Link: LeetCode

1. The one idea that solves it

At every index i, you already know what the other number must be: target - nums[i]. The only question is "have I seen that number earlier?". A hash map answers that in O(1).

So the brute-force double loop (O(n2)) collapses to one left-to-right pass. As you walk, you build a map of value → index. Before inserting the current number, you check if its complement is already in the map.

Idea. Trade space for time. One pass, one hash map. For each nums[i], look up target - nums[i]. If it is in the map, you have the answer; otherwise insert nums[i] and continue.

Why not sort and use two pointers?

Sorting plus two pointers is O(n log n) and loses the original indices (you would have to pair each value with its index first). The hash-map pass is O(n) and keeps indices for free. The sorted + two-pointer idea is still worth knowing because LC 167 Two Sum II is exactly that: input already sorted, return 1-based indices. The L/R two-pointer shape appears in the other problems on this page (11, 15, 42).

4. Code (C++)

class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        unordered_map<int, int> seen;         // value -> index
        for (int i = 0; i < (int)nums.size(); i++) {
            int need = target - nums[i];
            auto it = seen.find(need);
            if (it != seen.end()) return {it->second, i};
            seen[nums[i]] = i;                   // insert AFTER the check
        }
        return {};
    }
};

Complexity: one pass, O(1) expected work per index. O(n) time, O(n) space for the map.

Alternative: sort + two pointers (works only if indices do not matter)

int l = 0, r = nums.size() - 1;
sort(nums.begin(), nums.end());
while (l < r) {
    int s = nums[l] + nums[r];
    if (s == target) return {nums[l], nums[r]};
    if (s < target) l++;
    else r--;
}

O(n log n) time, O(1) extra space, but sorting destroys the original indices. Use this shape for LC 167 (sorted input) and as a building block in LC 15 3Sum.

5. The part interviewers ask about: insert AFTER the check

If you insert nums[i] into the map before checking the complement, the input [3,3], 6 breaks: at i = 0 you store 3 → 0, and when you look up the complement 3 you find index 0 and return [0, 0], reusing the same element. Check first, insert after.

Equivalently: on duplicate keys, let the later write overwrite. That is fine, because by the time a duplicate value appears, you have already looked it up and either returned or moved on. The map only needs to answer "has the complement been seen at any earlier index?" and any earlier index works.

6. Traps and edge cases

  • Reusing the same element. Fixed by looking up the complement before inserting. The pair [3,3], 6 is the canonical test.
  • Negative numbers and zero. Nothing special. [-3,4,3,90], 0 → [0,2] works.
  • Overflow. With 32-bit ints, target - nums[i] can overflow in theory. LC constraints keep -109 ≤ nums[i], target ≤ 109, so an int subtraction fits (worst case 2×109 is above INT_MAX). Use long long for need if the range were larger.
  • Sorting then returning sorted indices. LC wants indices into the original array. If you sort, pair values with their original indices first.
  • No answer. The problem guarantees exactly one, but defensive code returns {}.

7. How to say it in the interview (30 seconds)

"I keep a hash map of value to earliest index. I walk the array once. At each index, I look up target - nums[i]. If it is in the map, I return that index and the current one. Otherwise I insert nums[i] and continue. The key subtlety is to look up before inserting, so a duplicate value cannot pair with itself. One pass, O(n) time and O(n) space."
