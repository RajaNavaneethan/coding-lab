Valid Parentheses

LeetCode 20 · Easy · Pattern: stack of expected closers · O(n) time, O(n) space

Problem. Given a string of brackets ()[]{}, decide if every opener has a matching closer of the same type, in the correct nested order.
"()[]{}" → true   "([)]" → false   "{[]}" → true
Link: LeetCode

1. The one idea that solves it

Brackets have to close in the reverse order they open. That is literally what a stack does: last in, first out. So walk the string left to right. On every opener push what you expect to see next; on every closer, that expected char must be sitting on top of the stack.

A tidy trick: instead of pushing the opener and matching it later, push the closer that must come next. Then on a closing bracket you just check equality with the top. No lookup table on the hot path.

Idea. Walk the string. Opener → push its matching closer. Closer → it must equal the top of the stack; pop. At the end the stack must be empty. "Expected to close next" is always on top.

4. Code (C++)

class Solution {
public:
    bool isValid(string s) {
        stack<char> st;
        for (char c : s) {
            if (c == '(' || c == '[' || c == '{') {
                st.push(c == '(' ? ')' : c == '[' ? ']' : '}');
            } else {
                if (st.empty() || st.top() != c) return false;
                st.pop();
            }
        }
        return st.empty();
    }
};

Complexity: each character pushed and popped at most once. O(n) time. Worst case the input is all openers, so the stack can hold n entries. O(n) space.

5. The part interviewers ask about: why pushing the closer is clean

The alternative is to push the opener and, on a closer, check that the top is the matching opener via a tiny map (')' → '(', etc). It works, but there is an extra lookup on every closer. Pushing the closer directly makes the inner check a single c != st.top(). In an interview, call out that both are O(n) and pick whichever is clearer to you. The underlying invariant is the same: the top of the stack is always the next closing bracket we expect to see.

A second subtle point: three distinct final states collapse to reject: closer with an empty stack (nothing to match), closer whose required char does not match the top (wrong type), and a non-empty stack at the end (opener never closed). The code handles the first two in the loop and the third with st.empty() at the end.

6. Traps and edge cases

  • Forgetting the empty-stack guard before st.top(). On input ")" this is undefined behaviour. Check st.empty() || st.top() != c in that order.
  • Forgetting the final emptiness check. On input "(" the loop never rejects. Return st.empty(), not true.
  • Checking st.top() == c as the acceptance condition without popping on success. You keep the expected closer on the stack and reject the next character for no reason. Always pop after a match.
  • Treating "[" and "]" as interchangeable with "(" and ")". Each type must match its own kind. "([)]" is false because the ) arrives while the top is ].
  • Edges. "" → true (no obligations). Single opener "(" → false. Single closer ")" → false. Odd-length input is always false (optional micro-optimisation: return early).

7. How to say it in the interview (30 seconds)

"Brackets close in reverse order of opening, so I use a stack. When I see an opener I push the matching closer onto the stack. When I see a closer I check it equals the top of the stack and pop. If the stack is empty on a closer or the top does not match, it is invalid. At the end the stack must be empty, otherwise some opener was never closed. O(n) time, O(n) space."
