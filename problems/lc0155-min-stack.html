Min Stack

LeetCode 155 · Medium · Pattern: pair each value with the min at its level · O(1) per op, O(n) space

Problem. Design a stack with the usual push, pop, top, plus getMin which returns the minimum value currently in the stack. Every operation must run in O(1).
Example: push(-2) push(0) push(-3) getMin() → -3, pop(), top() → 0, getMin() → -2
Link: LeetCode

1. The one idea that solves it

The minimum changes only on push (it can go down) and pop (an old min can come back). A plain stack of values forgets the old min as soon as a smaller one arrives, which is why a naive getMin is O(n).

Fix: store two numbers per level instead of one — the value you pushed, and the minimum of everything in the stack up to and including this level. When you push x, the new level's min is min(old-top-min, x). Each level now remembers the min for the stack snapshot it belongs to, so a pop automatically restores whatever min was true before.

Idea. Each cell on the stack is a pair (val, minSoFar). push(x) → push (x, min(prev.minSoFar, x)). pop drops the top pair, restoring the previous min for free. getMin() reads top.minSoFar. All O(1).

4. Code (C++)

class MinStack {
    stack<pair<int, int>> st;        // (val, min at this level)
public:
    MinStack() {}
    void push(int val) {
        int m = st.empty() ? val : min(st.top().second, val);
        st.push({val, m});
    }
    void pop()      { st.pop(); }
    int  top()      { return st.top().first; }
    int  getMin()   { return st.top().second; }
};

Complexity: each operation does a constant number of stack ops. O(1) per op, O(n) space for the pairs. The problem guarantees pop, top, getMin are only called on a non-empty stack, so no emptiness guards are needed inside those three.

Alternative: two stacks (values + running minima)

stack<int> vals, mins;
void push(int x) {
    vals.push(x);
    mins.push(mins.empty() ? x : min(mins.top(), x));
}
void pop()    { vals.pop(); mins.pop(); }
int  top()    { return vals.top(); }
int  getMin() { return mins.top(); }

Exactly the same amount of memory (two stacks of n ints = n pairs). Pick whichever reads cleaner for you; the pair version is one container to maintain.

Space-optimised variant (push the min only when it changes)

You can push onto the mins stack only when a new, equal-or-smaller min arrives, and pop from it only when you pop a value that equals the current min. Saves memory on long runs where the min does not change often, but adds a <= compare on every op. In an interview, mention it as "constant factor win, not asymptotic".

5. The part interviewers ask about: why ≤ matters in the space-optimised version

In the space-optimised variant you must push onto the mins stack on equal too, not just strictly less. Example: push(1), push(1), pop(). If you only pushed 1 once, then after pop() you would pop the 1 off mins and getMin would return a stale value (or crash on an empty mins). Pushing on ≤ keeps one entry per level that can see 1 as the min, so pop pairs up correctly. The paired-cell version avoids this question because every level has its own minSoFar by construction.

The real invariant: at every level i, minSoFar[i] = min(val[0..i]). It is maintained by induction on push, and pop deletes the last level so the invariant on the remaining levels was already true. That is the whole proof.

6. Traps and edge cases

  • Tracking a single running minimum variable. On pop you cannot recover the previous min without walking the whole stack. The minimum must be remembered per level.
  • Computing the new min as min(oldVal, x) instead of min(oldMinSoFar, x). You compare against the previous top value, not the min of everything underneath it. On push(5), push(2), push(7) you would set the min at level 3 to min(2, 7) = 2 only by luck; try push(5), push(10), push(7) and you would get min(10, 7) = 7 instead of 5.
  • INT_MIN as a sentinel for "empty". Breaks the moment the input legitimately pushes INT_MIN. Use st.empty() instead.
  • Duplicates equal to the current min. Pushing the same min twice is fine with pairs; it is the trap in the space-optimised variant. See section 5.
  • Calling pop / top / getMin on an empty stack. The problem forbids it. In production code you would throw or return a sentinel; here just trust the contract.

7. How to say it in the interview (30 seconds)

"I store each stack level as a pair: the value, and the minimum of the stack up to and including that level. On push(x) the new level's min is min(prevTopMin, x). pop drops the pair, which restores the previous min automatically. getMin is just top.minSoFar. All four operations are O(1), using O(n) space. The alternative is two parallel stacks for values and mins, same complexity."
