Daily Temperatures

LeetCode 739 · Medium · Pattern: monotonic decreasing stack of indices · O(n) time, O(n) space

Problem. Given temperatures[i], return ans[i] = the number of days until a strictly warmer day, or 0 if there is no warmer day in the future.
[73,74,75,71,69,72,76,73] → [1,1,4,2,1,1,0,0]
Link: LeetCode

1. The one idea that solves it

This is a next-greater-element problem. The brute force is quadratic: for each day, scan forward until you find a warmer one. The waste is obvious: once a cold day has been "satisfied" by day i, we never need to re-check it. We want a data structure that holds the days still waiting for a warmer future.

Hold the indices of unresolved days on a stack. Keep the stack so that temperatures from bottom to top are strictly decreasing. When a new day i arrives:

  • Any day on top of the stack with t[top] < t[i] is now resolved: its answer is i - top. Pop it.
  • Repeat until the stack is empty or the top is not strictly colder than t[i].
  • Push i. The stack stays decreasing.

Every index is pushed exactly once and popped at most once, so total work is O(n).

Idea. Monotonic decreasing stack of indices. A new, warmer day pays off all colder waiting days on top at once. The gap i − top is the answer for the day being popped.

4. Code (C++)

class Solution {
public:
    vector<int> dailyTemperatures(vector<int>& t) {
        int n = (int)t.size();
        vector<int> ans(n, 0);
        stack<int> st;                       // indices, temps strictly decreasing bottom->top
        for (int i = 0; i < n; i++) {
            while (!st.empty() && t[i] > t[st.top()]) {
                int j = st.top(); st.pop();
                ans[j] = i - j;                 // first warmer day for j is i
            }
            st.push(i);
        }
        return ans;
    }
};

Complexity: each index is pushed once and popped at most once. O(n) time. The stack can hold all n indices in the worst case (strictly decreasing input), so O(n) space.

Alternative: O(1) extra space, walk right to left

int n = t.size();
vector<int> ans(n, 0);
for (int i = n - 2; i >= 0; i--) {
    int j = i + 1;
    while (j < n && t[j] <= t[i]) {
        if (ans[j] == 0) { j = n; break; }  // no warmer day exists after i either
        j += ans[j];                              // jump over "known loser" runs
    }
    if (j < n) ans[i] = j - i;
}

Same O(n) amortised time because ans[j] lets you skip entire blocks that cannot beat t[i]. Reuses the output as scratch space, so no explicit stack. Slick but harder to explain under time pressure; use the monotonic stack as the first answer.

5. The part interviewers ask about: why strictly greater, and why indices

Strict > in t[i] > t[st.top()] matters because the problem says "strictly warmer". If you wrote ≥, equal temperatures would pop each other and count the same day as "warmer", giving a wrong answer. On [70,70,71] the right output is [2,1,0], not [1,1,0].

Indices, not values, because the answer is a distance. If the stack stored temperatures you would still need an index to compute i - j. Indices give you the temperature via one array lookup (t[st.top()]) and the distance for free.

The invariant "temperatures on the stack are strictly decreasing bottom to top" is maintained by the while loop: before pushing i, we have popped every top whose temperature is strictly below t[i], so either the stack is empty or the top is ≥ t[i]; pushing i keeps the sequence non-increasing, and the strict comparison also keeps duplicates on the stack in order (an earlier day with the same temperature stays below a later one — good, because it is still waiting for a strictly warmer day).

6. Traps and edge cases

  • Pushing temperatures instead of indices. You lose the ability to compute the distance in O(1).
  • Using ≥ in the pop condition. Equal temperatures leak answers to each other and you get wrong distances on runs of equal temperatures.
  • Initialising ans with something other than 0. Any index left on the stack at the end never saw a warmer day, so its ans must be 0. The vector's default value handles this; don't overwrite it.
  • Walking the stack to clear it at the end. Unnecessary: untouched entries already have ans = 0. Writing a loop here is a tell that the invariant is not clear in your head.
  • Strictly decreasing input. [76,75,74] never pops. Stack grows to size n, all answers are 0. This is the O(n) space worst case.
  • Length-1 input. [73] → [0]. The outer for handles it; no while body runs.

7. How to say it in the interview (30 seconds)

"I keep a stack of indices for days that are still waiting for a warmer day. The temperatures on the stack are strictly decreasing from bottom to top. For each new day i, I pop every index on top whose temperature is strictly less than t[i] and set its answer to i − j. Then push i. Each index is pushed once and popped at most once, so O(n) time and O(n) space. Any index still on the stack at the end never got a warmer day, so its answer stays 0."
