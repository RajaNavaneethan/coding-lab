Sliding Window Maximum

LeetCode 239 · Hard · Pattern: fixed-size window with a monotonic deque · O(n) time, O(k) space

Problem. Given nums and a window size k, return an array where the i-th entry is the maximum of nums[i..i+k-1].
nums = [1,3,-1,-3,5,3,6,7], k = 3 → [3,3,5,5,6,7]
Link: LeetCode

1. The one idea that solves it

Scan left to right and keep a deque of indices whose values are strictly decreasing from front to back. The front is the index of the current window's maximum.

Two invariants, maintained at every step:

  1. Front is in range: if the front index is ≤ i − k, it has slid out of the window. Pop from the front.
  2. Values are decreasing: before pushing index i, pop from the back while nums[back] < nums[i]. Those older indices cannot ever be the max again, because nums[i] is both bigger and stays in the window at least as long as they do.
So the question becomes: on each step, drop out-of-window elements from the front, drop smaller elements from the back, then push the current index. Once i ≥ k − 1, the front of the deque is the answer for window [i − k + 1, i].

Why strict "smaller" is right (not ≤): equal values must both survive, otherwise you lose the later one too early. Later-equal is kept because it leaves the window later; earlier-equal is kept because at this moment it is a valid max. Using < on pop keeps both. Using ≤ would still be correct for the max output, but you would lose some index information useful in follow-up problems.

4. Code (C++)

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    deque<int> dq;                                      // indices, values decreasing
    vector<int> out;
    for (int i = 0; i < (int)nums.size(); i++) {
        while (!dq.empty() && dq.front() <= i - k) dq.pop_front();         // out of window
        while (!dq.empty() && nums[dq.back()] < nums[i]) dq.pop_back();     // no longer useful
        dq.push_back(i);
        if (i >= k - 1) out.push_back(nums[dq.front()]);
    }
    return out;
}

Complexity: every index is pushed once and popped at most once, so O(n) amortised across the whole scan. The deque holds at most k indices, so O(k) extra space.

Alternative: max-heap of (value, index)

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    priority_queue<pair<int, int>> pq;                 // (value, index)
    vector<int> out;
    for (int i = 0; i < (int)nums.size(); i++) {
        pq.push({nums[i], i});
        while (pq.top().second <= i - k) pq.pop();          // lazy delete
        if (i >= k - 1) out.push_back(pq.top().first);
    }
    return out;
}

Easier to code under pressure, O(n log n) time, O(n) space in the worst case because the heap keeps stale entries until they bubble up. Prefer the deque in C++; use the heap when the language's deque feels clunky (older Java APIs, Python collections.deque is fine but index arithmetic is finicky).

5. The part interviewers ask about: why O(n) amortised

Every index i enters the deque exactly once (one push_back). Once removed, it is never re-inserted. So across the whole loop the total number of pushes is n and the total number of pops (front plus back) is at most n. The inner while loops look suspicious, but their total work across all iterations is bounded by the number of pops, which is at most n. Hence O(n).

Why the back-pop is safe. Suppose nums[dq.back()] < nums[i]. Any future window containing dq.back() also contains i (because i is to the right of dq.back() and will leave the window later or at the same time). So in every future window the smaller value is dominated by the larger one and cannot be the max. Safe to discard.

Common follow-up: sliding window minimum. Flip the direction. Keep an increasing deque; pop from the back while nums[back] > nums[i].

Harder follow-up: range queries at arbitrary indices. If the window stops being contiguous, a monotonic deque no longer suffices; use a sparse table (O(n log n) build, O(1) query) or a segment tree.

Why does the front always give the answer? After the two pops, every index remaining in the deque is > i − k (in-window) and its value is strictly greater than every value to its right in the deque. So the leftmost one is the biggest in-window value — that is the maximum.

6. Traps and edge cases

  • Comparing values instead of indices for the front pop. You must drop by position (front ≤ i − k), not by value. A big value can slip out of the window and still be the front.
  • Using ≤ instead of < on the back pop. Still produces correct maxes, but you can lose equal values prematurely; a few LC follow-up variants break.
  • Recording output before i ≥ k - 1. The first full window ends at index k - 1; earlier outputs would use partial windows.
  • Starting with an empty window (k = 0). The problem guarantees k ≥ 1, but defend against it: return empty.
  • k > n. No full window exists; return empty.
  • Using size_t for i - k. That can wrap around when i < k. Keep the comparison front + k ≤ i instead, or use int.
  • Rebuilding the deque from scratch each step. O(nk); the whole point is to reuse state.

7. How to say it in the interview (30 seconds)

"I maintain a deque of indices whose values are strictly decreasing from front to back. The front is always the max of the current window. Before pushing index i, I pop smaller values from the back (they can never be the max again) and I pop the front if it has slid out of the window. Once the window is full, I append the value at the deque's front to the answer. Each index is pushed and popped at most once, so O(n) time, O(k) space."
